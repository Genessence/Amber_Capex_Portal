## Architecture

**Capex Amber** is a Next.js 16 app (App Router, TypeScript, Tailwind v4) for Amber Enterprises' CAPEX procurement workflow. Entirely client-side — no backend, no database. All state lives in `CapexProvider` and is persisted to `localStorage` under the key `capex_data_v2`. **Large base64 file blobs** (Proforma Invoices, PO + technical-spec documents, quote/line-item/land attachments) are kept OUT of the localStorage payload and stored in **IndexedDB** (`src/lib/fileStore.ts`) so the workflow state always fits the ~5 MB quota and never fails to persist; the provider strips base64 on write (`stripRequestFiles`/`stripInviteFiles`) and async-hydrates it back on load (`hydrateRequestFiles`/`hydrateInviteFiles`). This is self-migrating — older inline-base64 localStorage data shrinks on the next write. **The IndexedDB write waits for hydration** (`filesHydrated` ref in `CapexProvider`): until the stored blobs have been merged back into state, the in-memory state is lean, and persisting it would overwrite the file map with an empty object and destroy every stored blob.

### Auth model

Mock-only. `LoginPage` writes the selected role to `localStorage("capex_role")`. `LoginGate` redirects to `/login` if absent. `TopNav` exposes a role-switcher dropdown that writes the same key and fires a `capex_rolechange` CustomEvent. All role-aware components listen to that event.

Roles: `buyer`, `buyer_jhajjar_p1`, `buyer_jhajjar_p2`, `sourcing_member`, `maintenance`, `super_admin`. **The `plant_head*` and `sourcing_head` roles were removed (2026-07)** — plant-head approvals happen via a public emailed link (see **Workflow overhaul (2026-07)**), and the sourcing team finalizes vendors with no head gate.

`maintenance` (authors next-FY Brown Field budget proposals) is **global** (not plant-scoped) and is registered in the same places as other roles (`ROLE_NAMES`, `Sidebar.ROLE_META` + `NAV`, `TopNav.ROLE_GROUPS`, `login` `ROLES`).

**The `plant_accounts` and `accounts` roles were removed (2026-07) — see *Accounts teams moved to email* below.** `RETIRED_ROLES` in `constants.ts` lists every retired role value; `LoginGate` clears a stale `capex_role` that matches one and bounces the browser to `/login` (otherwise the user would land in a portal with no navigation).

Plant-scoped roles (`buyer_jhajjar_*`) filter data to their plant. `ROLE_PLANT` in `constants.ts` maps these roles to their plant value; roles absent from the map have access to all plants.

### Workflow overhaul (2026-07)

A set of changes reshaping approvals, sourcing, and fulfillment. **These supersede the older descriptions further down where they conflict.**

**Accounts teams moved to email (roles removed, 2026-07).** Neither accounts team has a portal login any more; both act on tokenised public links, exactly like the plant head and the Technical team.

**The fulfillment track is split across two public links** that resolve to the same request/award — `resolvePoTarget` matches either token and returns a **`stage`** (`'plant_accounts' | 'po_issue'`); each page rejects the other's token outright, so one link can never do the other's job.

- **Plant Accounts** — `src/app/(public)/po/[token]/page.tsx`, token `poToken` (minted when the vendor submits the PI; backfilled by `normalizeRequest`/`normalizeInvite`). They assign the **FA codes**, and after the PO is out they tick the **payment milestones**. Every mutation is stamped `'Plant Accounts (email)'`. A step rail (FA codes → PO (Satish) → Payments → Done) shows where the track stands.
- **Global Accounts ("Satish")** — `src/app/(public)/po-issue/[token]/page.tsx`, token `poIssueToken` (minted by **`submitFaCodes`**, backfilled at `accounts_processing`). He assigns the PO number, uploads the PO document(s) and **issues the PO** (`issuePurchaseOrder`, stamped `'Global Accounts (Satish)'`, invite path turn-guarded to `accounts_processing` so a stale link can't overwrite an issued PO). He *also* casts the final budget sign-off (below) — same person, same address (`GLOBAL_ACCOUNTS_EMAIL` / `GLOBAL_ACCOUNTS_NAME`).
- **The FA → PO handoff email is sent by Plant Accounts from their own public page.** Submitting the FA codes mints Satish's token in the same state pass and **auto-opens `EmailPreviewModal`** pre-filled with the items + FA codes + his link; the panel stays on the page for copy-link / re-send / open.
- Full chain: vendor PI → Plant Accounts FA codes → *(email)* → Satish issues PO → vendor **re-uploads the PI** → `completed`. **The flow ENDS at the PI re-upload (2026-09)** — see *Payment milestones removed* below; the advance / final-payment ticks no longer exist.
- **Global Accounts' budget sign-off** — the final `pending_accounts` gate on a next-FY proposal, at `/approve/<accountsToken>`. `BudgetProposal.accountsToken` is minted when the super admin approves at the admin stage, **burned on decision**, and cleared on resubmit/needs-correction/reject. `resolveApprovalTarget` returns a `stage: 'plant_head' | 'accounts'` on budget targets so one public page serves both gates. **Because the token is burned, the approve page checks its local `done` state BEFORE the `!target` guard** — otherwise the target is already gone on the render right after a decision and the approver sees "Link Invalid or Expired" instead of the confirmation. It also keeps the last resolved stage in a ref (`issuedTo`), so the confirmation keeps the right header and the accounts wording ("published as the live FY budget"). The `tech-spec` page already orders these correctly; the `po`/`po-issue` tokens are not burned, so they resolve fine after the action.
- **Every handoff exposes copy-link + preview-email**, mirroring the plant-head affordance: `AccountsPanel` (stage-aware — Plant Accounts' link at `pi_submitted`/`payment_in_progress`, Satish's at `accounts_processing`), the Plant-Accounts page itself, and `/capex/budget-approvals` for the budget sign-off. All use `EmailPreviewModal`.
- **`AccountsPanel` is now READ-ONLY** for every internal role — it tracks the PI / FA codes / PO / milestones and carries the stage-appropriate handoff affordance. `/accounts/queue` is likewise a read-only tracker (`sourcing_member` + `super_admin`), and `/capex/budget-approvals` is `super_admin` only.
- Because the Global-Accounts approval publishes master rows from a **public tab**, the cross-tab `storage` listener re-syncs **`capexMaster`** as well as requests/invites/budgetProposals.

**Payment milestones removed — the track ends at the vendor's PI re-upload (2026-09).** Plant Accounts no longer tick payment checkboxes. After Global Accounts issue the PO, the vendor re-uploads the PI against it, and that **completes** the award / request (stamps `piReuploadedAt` + `tatStoppedAt`; a split-award request completes once every award has). The rest of the chain is unchanged.
- **`issuePurchaseOrder(requestId, po, actor, inviteId?, note?)`** no longer takes or builds milestones. **`markPaymentMade` is removed.** The status key **`payment_in_progress` is kept for data compatibility** but now means "PO issued — awaiting the vendor's PI" (`STATUS_LABELS`: *PO Issued — Awaiting PI*).
- **`resubmitProformaInvoice`** is the final mutation. It is gated on `payment_in_progress` + no `piReuploadedAt`, and deliberately **not** on `piReuploadAllowed`, which the retired payment ticks used to clear. Keying on that flag would strand legacy tracks that were already part-paid.
- **Trials still gate completion.** The vendor uploads the trial once the PO is issued (not after an advance). The track completes when **both** the PI re-upload and the trial approval are done, whichever comes last: `fulfillmentReadyToComplete` in `paymentUtils.ts` is checked by both `resubmitProformaInvoice` and `respondToTrial`.
- Plant Accounts' `/po/[token]` page is FA codes plus a read-only status, with the step rail *FA codes → PO → Vendor PI re-upload → Done*. `AccountsPanel` hides its handoff link once the PO is issued, because the vendor holds the ball from then on. `ballHolders` returns `vendor` at `payment_in_progress`, or `sourcing` while a trial awaits review. Legacy `paymentMilestones` / `advancePaidAt` fields stay on the types but nothing writes them any more.

**Plant head via public email link (roles removed).** `plant_head*` and `sourcing_head` are removed from all registries/gates. Plant-head approval (budget + request) now happens through a **tokenised public page** `src/app/(public)/approve/[token]/page.tsx`, resolved by `resolveApprovalTarget(token, requests, budgetProposals)` in `tokenUtils.ts` (token minted by `generateApprovalToken` — CSPRNG; `buildApprovalLink`). The internal side shows a **copy-link + email-preview** affordance (`EmailPreviewModal`, the generalized `FaEmailModal`) at each handoff. On the request detail (`capex/[id]`) the plant-head approval panel (copy link + preview email) renders for **all internal roles including the buyer/requester** while `pending_head_approval`, so the requester can send the link to the plant head. `CapexRequest.approvalToken`/`BudgetProposal.approvalToken` carry the tokens (backfilled in `normalizeRequest`). Public mutations: `decideRequestPlantHead(requestId, decision)` and `decideBudgetPlantHead(id, decision)` (state-guarded). The context `storage` listener re-syncs `budgetProposals` too so a decision in the public tab reflects internally.

**Request routing.** `initialStatusForRequest`: **only Green Field skips head approval** (`→ sourcing`); Brown Field + Digitisation + IT all `→ pending_head_approval`.

**Budget approval = multi-stage.** `BudgetProposalStatus`: `draft → pending_plant_head → pending_admin → needs_correction → pending_accounts → approved | rejected`. `submitBudgetProposal` → `pending_plant_head` (rotates token, restarts from plant head on rework, clears prior-stage stamps); `decideBudgetPlantHead(id, decision, note?, editedItems?)` → `pending_admin` (approve) / `needs_correction` / `rejected`; `decideBudgetProposal(id, decision, actor, note?, editedItems?)` (super-admin) → `pending_accounts` (approve, **no publish**) / `needs_correction` / `rejected`; `decideBudgetAccounts` (**Global Accounts, on the public `/approve/<accountsToken>` page**) → `approved` + **publish to `capexMaster`** (reads target from committed state before mutating; guarded by `pending_accounts`; burns `accountsToken`). **Approvers EDIT the budget and send it FORWARD, never back (2026-08).** Both the plant head (public page) and the super admin get **Edit & Send Forward** — the shared **`BudgetEditForwardPanel`** (`src/components/BudgetEditForwardPanel.tsx`, replaces the removed `BudgetCorrectionPanel`) lets them adjust any line's head / sub-particulars / department / qty / budget (or add / remove lines), add a remark for the next stage, and **approve with those edits applied in one pass** — `decideBudgetPlantHead(id,'approved',note,editedItems)` → `pending_admin`, `decideBudgetProposal(id,'approved',actor,note,editedItems)` → `pending_accounts`. The panel shows a live `submitted → revised (Δ)` figure and a **Reset edits** control. Each edit appends a `BudgetProposalEdit` to `BudgetProposal.edits` (stage, approver, timestamp, remark, lines + total before/after) via `applyApproverEdit` in `budgetProposalUtils.ts`; the trail renders at the top of `BudgetProposalBreakdown` ("Revised in approval"), so the **next** approver sees exactly what changed. A no-op edit (panel opened, nothing changed, no remark) records nothing. `edits` is cleared on (re)submit. The only backward moves left are **Reject** and the retained-but-unsurfaced `needs_correction` mutation branch (legacy proposals stuck in that state still resubmit normally). `/capex/budget-approvals` is **`super_admin` only**: they decide the admin stage, then share the Global-Accounts sign-off link (copy / preview email) for the accounts stage. **Every approver reviews the same full breakdown** — the shared **`BudgetProposalBreakdown`** (`src/components/BudgetProposalBreakdown.tsx`) lists the proposal grouped by head with **each sub-particular** (department, qty, rate, budget), a per-head subtotal, and a grand total. The old per-head *diff vs live FY* view (Live / Proposed / Δ columns) was **removed** from the approval surfaces — approvers see the proposed FY budget itself, not a delta — along with the now-unused `diffProposalAgainstLive`/`summarizeMasterByHead`/`HeadDiffRow` helpers. Authors: `maintenance`, `sourcing_member`, `super_admin` (Green Field: `maintenance` + `super_admin` only — see the Green Field section). **On `/capex/requests` the `maintenance` (budget-upload) user sees a BUDGET-approval-requests list** (their proposals + status + correction remark + Edit/Resubmit link), not item requests.

**Sourcing head removed → award goes straight to PI.** `canFinalize` = the sourcing team (`sourcing_member`/`super_admin`) everywhere (`FinalDecisionActions`, `VendorGrid`, `RfqPanel`, `capex/[id]`).

**Start Reverse Auction asks for the auction document FIRST (2026-09).** The RFQ panel's **Start Reverse Auction** button no longer escalates on a `window.confirm`. It opens a **Configure Auction Document** popup, the same **`AuctionDocumentForm`** (`src/components/AuctionDocumentForm.tsx`) the reverse-auction panel uses for its own setup card, so there is one implementation for both entry points. The popup covers dates/times, bidder-acceptance + vendor-revert deadlines, Green Field delivery locations, the auction rules, duration and threshold.

On submit (`escalateToAuction` in `RfqPanel`), in this order:
1. `saveAuctionApprovalDocument`
2. `sendAuctionApprovalToVendors` to every vendor who quoted in the RFQ
3. `seedAuctionFromRfq`
4. `setSourcingMode('auction')`

The document therefore reaches every vendor before the page flips to auction mode, and each vendor lands on the Business Rules approval screen, never a bid form. The countdown still starts from the auction panel's **Start Auction** once ≥1 vendor has approved, which is unchanged. The popup's **duration + threshold are stamped on the document** (`AuctionApprovalDocument.durationDays` / `threshold`), because the popup and the Start Auction control live in different components; `ReverseAuctionPanel` initialises from them.

**Reverse auction: 5% + rank reset.** On escalation, `seedAuctionFromRfq` seeds each vendor's opening bid onto `VendorInvite.openingQuote` (**not** `quotes[]`, and `price` = base subtotal per the auction-bid convention) so `computeVendorRankings` stays empty until a fresh bid. `setAuctionConfig` sets `auctionConfig.openingBestPrice = min(current best, INR basis) × 0.95` — the whole-quote "price to beat", shown on the internal auction panel. Award-price fallback (`resolveFinalVendor`, `VendorGrid` auto-fill) reads `quotes.at(-1) ?? openingQuote`.

**Auction best price — whole quote, opens at −5% (2026-07).** The auction has **one** price to beat, for the whole quote; there is deliberately **no per-line-item best price** on the vendor screen. It **opens** at the lowest RFQ quotation **− 5%** and thereafter moves **only when a vendor actually beats it**: a live bid below the opening price becomes the new best price, while bids above it leave the opening price standing (`Math.min(openingBest, lowestLiveBid)`). `computeAuctionBestPrice(invites, lineItems?, config?)` in `auctionUtils.ts` returns `number | null`; `AUCTION_DECREMENT` (0.05) and `applyAuctionDecrement` are exported alongside. The opening figure prefers the stored `config.openingBestPrice` (stamped by `setAuctionConfig` at setup) and derives from `openingQuote → rfqQuote` only for auctions configured before that field existed — **`quotes` is never read for the opening**, because `submitQuote` overwrites it in place so it only ever holds the vendor's *current* bid. Everything is derived on demand from data every auction already has, so **in-flight auctions pick this up with no backfill or migration**. Comparison is on an **INR basis** (`toInr`) so a foreign-currency quote isn't mistaken for the lowest.

**The supplier auction screen does NOT show the best price (2026-09).** A vendor sees only **their own rank and their own bid**: the summary card has two boxes (Your Rank · Your Bid Total), and the old "Best Price" box and every "₹X above best price" hint (rank card + sticky bar) are removed, since a gap reveals the best price by subtraction. `computeAuctionBestPrice` is no longer called on the supplier page; the price to beat stays visible to **sourcing** on the internal auction panel. Rank itself still comes from real bids (`computeVendorRankings`). Note `computeVendorRankings` ranks on `Quote.price` (the base subtotal) while the best price is the **whole-quote** total including freight/packing/service — the same basis `setAuctionConfig` uses for `openingBestPrice`.

**Technical specification approval (pre-award gate, PER VENDOR — 2026-07).** Before sourcing can finalize a vendor and request their Proforma Invoice, the machine's technical specification must be signed off by **Amber's Technical team**. The gate is **per vendor** (different vendors supply different machines, and split awards hand different lines to different vendors). Sourcing prepares the package in the **`TechSpecPanel`** (`src/components/TechSpecPanel.tsx`, rendered above `FinalDecisionActions` in BOTH the RFQ panel and the auction view on `capex/[id]`): **upload the spec document(s) the vendor provided** (`TechSpecDocument`, `fromVendor: true`, ≤6 files × 2 MB, base64 offloaded to IndexedDB under `techspec:<id>`) plus free-text notes, then **Send to Technical team**. The Technical team has **no portal login** — they act on a tokenised **public page** `src/app/(public)/tech-spec/[token]/page.tsx` (`resolveTechSpecTarget`/`generateTechSpecToken`/`buildTechSpecLink` in `tokenUtils.ts`; recipient `TECHNICAL_TEAM_EMAIL`, copy-link + `EmailPreviewModal` on the sourcing side). That page shows the request, the line-item specs, sourcing's notes, and downloadable documents, and offers **Approve / Send Back for Revision / Reject** (a remark is **required** for the latter two).

**The vendor's identity is WITHHELD from the Technical team (2026-08)** — they assess the machine on technical merit alone. The public page renders an anonymous **`anonymousVendorRef(inviteId)`** (`SPEC-XXXXXX`, FNV-1a over the invite id → stable across re-sends and token rotations; the `SPEC-` prefix deliberately avoids looking like a real `VND-001` vendor code) instead of the vendor name, with an on-page notice explaining the withholding. Document **filenames are replaced too** (`anonymousDocumentLabel` / `anonymousDocumentFileName` → "Specification Document 1 · PDF", downloaded as `specification-document-1.pdf`), because vendors routinely name their datasheets after themselves. The page no longer reads `vendors` at all. The **email that carries the link** uses the same reference in its subject and body. On the sourcing side `TechSpecPanel` shows the reference next to the real vendor name (so the two can be tied together internally) plus a notice telling sourcing to keep the vendor's name out of the notes — the one free-text field that reaches the Technical team. Send-back → `needs_revision` with the remark shown to sourcing, who revises and **re-sends** (token **rotated**, prior decision stamps cleared); the loop repeats until approved. The token is **burned on decision** so a stale link cannot re-decide.

Types: `TechSpecStatus` (`not_sent → pending_technical → needs_revision | approved | rejected`), `TechSpecApproval`, `TechSpecDocument`, `TechSpecMessage` on `VendorInvite.techSpec`. Helpers in **`src/lib/techSpecUtils.ts`** (`effectiveTechSpecStatus`, `canSendTechSpec`, `canDecideTechSpec`, `isTechSpecReadyToSend`, **`techSpecBlocksAward`**, labels/colours/hints). Mutations: `saveTechSpecDraft(inviteId, {notes?, addDocuments?, removeDocumentId?})`, `sendTechSpecForApproval(inviteId, senderName, notes?)` (the `notes` arg keeps the save + send in **one state pass** — saving separately would read back stale), `decideTechSpec(inviteId, decision, deciderName, note?)` (turn-guarded to `pending_technical`). **The gate is enforced in the context, not just the UI:** `awardAndRequestPi`, `finalizeSplitAward`, and `requestProformaInvoice` all reject vendors whose spec is not `approved` (shared `techSpecBlockedVendorIds`), and `FinalDecisionActions` disables + explains the block per vendor. Every status other than `approved` blocks — including `not_sent`, so the step cannot be skipped.

**Trials (optional QA gate).** Sourcing toggles **Require an item trial** in a **"Sourcing setup"** card in the request-detail sourcing view (`capex/[id]`, visible pre-award to the sourcing team in BOTH RFQ and auction modes; `FinalDecisionActions` just shows an "ON" reminder). (The old **Import / Add Vendor** button was **removed (2026-07)** — it duplicated the RFQ panel's **Invite vendors / Invite new vendor**; vendors are added there in RFQ, and via the reverse-auction panel's **Select Vendors** in the auction path.) `awardAndRequestPi`/`finalizeSplitAward` propagate `request.trialRequired` → awarded invites. Types: `TrialStatus` (`not_required|pending_upload|pending_review|approved|rejected`), `TrialSubmission`, `TrialMessage` on both `CapexRequest` (single-vendor) and `VendorInvite` (awarded). After the **advance** milestone (first non-final) is paid, the vendor uploads via `submitTrial(inviteId)` (routes by `invite.awarded`); sourcing reviews with `respondToTrial(requestId, resp, inviteId?)` (approve → `approved`; reject → `rejected`, vendor re-uploads). `finalPaymentBlockedByTrial` blocks the `isFinal` milestone in `AccountsPanel` + `markPaymentMade` until approved. UI: `TrialCard` (`mode='upload'|'review'`), `trialUtils.ts` labels/colours. Both mutations are state-precondition-guarded.

**Delivery lead time → final-payment date.** Supplier delivery is now **days** (`RfqQuote.deliveryDays`/`Quote.deliveryDays`). `markPaymentMade` stamps `advancePaidAt` when the first non-final milestone is ticked; `expectedFinalPaymentDate(advancePaidAt, deliveryLeadDays(invite))` (`paymentUtils.ts`) is shown next to the final milestone.

**Fulfillment additions.** Multi-file PO: `PurchaseOrder.poDocuments[]` (offloaded to IndexedDB keyed `podoc:<id>`; capped at `MAX_PO_DOCS`). Two handoff emails, both simulated: internal → **`PLANT_ACCOUNTS_EMAIL`** with the Plant-Accounts link (`/po/[token]`, token `poToken`), and Plant Accounts → **`GLOBAL_ACCOUNTS_EMAIL`** ("Satish") with the PO-issue link (`/po-issue/[token]`, token `poIssueToken`). Helpers `generatePoToken` / `generatePoIssueToken` / `buildPoLink` / `buildPoIssueLink` / `resolvePoTarget` in `tokenUtils.ts`. Between PO issue and payments the vendor **re-uploads the PI** (`piReuploadAllowed` + `resubmitProformaInvoice`), and if `trialRequired` the vendor uploads a **trial after the advance** (final payment blocked until sourcing approves). Post-PO PI re-upload: `piReuploadAllowed` (auto-set on PO issue) + `resubmitProformaInvoice`. **The re-upload window closes on the FIRST payment (2026-07)** — `markPaymentMade` sets `piReuploadAllowed: false` on every tick (both the award and the request branch), because the PO is being settled against the PI on file and revising it after money has moved would change what was already paid. The supplier page additionally hides the card when any milestone is `paid`, so records paid before that clearing existed behave the same with no migration. The RfqPanel quick-add ("Invite new vendor") has a **Foreign vendor** checkbox → Incoterms. **A vendor added there WITHOUT that box ticked gets no Incoterms anywhere (2026-09)**: no status or doc is seeded (`inviteNewVendor` gates on `foreign`), and the form header plus the confirmation toast no longer mention Incoterms for a domestic vendor.

**Foreign vendors + currency.** `Vendor.foreign` (onboard modal + `inviteNewVendor`) decides who answers the Incoterms questionnaire (`incoTermsRequired` keys on `foreign`, not `oneTime`); the blank doc is seeded in `inviteVendors` for foreign vendors and the questions are asked **at quote submit** (see the INCO Terms section). **Currency:** new `src/lib/currencyUtils.ts` (`FX_TO_INR` static table, `toInr`, `formatCurrency`, `currencySymbol`, and **`inrWithNative` / `inrWithNativeLabel`** — the INR-primary-with-own-currency-beneath renderer the comparison grids use); `fmtCurrency(n, currency)` in `auctionTheme.ts` delegates. All cross-vendor comparisons + award/threshold/PO amounts use an **INR basis** (`inrRfqTotal` in `rfqUtils.ts`, `toInr` in `paymentUtils`/`VendorGrid`/`capexContext`); sourcing surfaces show the INR value with the original foreign amount below.

**INR-basis invariant — rank, order value, PI amount (2026-08).** Three surfaces broke the INR rule and were fixed:
- **`computeVendorRankings` (`auctionUtils.ts`) ranks on `toInr(quote.price, quote.currency)`.** `VendorRanking` now carries `price` (INR, the ranking + gap-to-L1 basis), `nativePrice` and `currency` (display only). The ranking basis is still the bid's **base subtotal**, while `computeAuctionBestPrice` is still the **whole quote** — that difference is deliberate and unchanged. The internal Vendor Ranking table shows the INR figure with the vendor's own-currency bid beneath, under a **`Bid Subtotal (₹)`** header, and the "Opening Price to Beat" above it is labelled **whole quote** — the two bases sit adjacent and are now named. The supplier bid screen converts before comparing, but **against two different bases**: `grandTotalInr` vs the auction best price, and `itemSubtotalInr` vs the **threshold** — i.e. **the threshold is compared against the bid SUBTOTAL, not the whole quote**, deliberately, with a comment at the comparison (`supplier/[token]/page.tsx`, `aboveThreshold`). Own-currency inputs and figures on that screen are labelled with `currencySymbol(currency)` / `fmtCurrency(n, currency)` — the bid table's `Unit Price`, `Item Price`, the three Additional Charges, the grand-total summary and the thread message written on submit. The `₹` figures that remain there are genuinely INR (rank card, best price, threshold, `PI Amount (₹)`). **One known exception:** the legacy counter panel's `Target Price` / `Max Freight` read `NegotiationMessage.counterPrice`/`counterFreight`, fields that carry **no currency at all**, so they are printed with `₹` on an unverified basis — fixing that needs a schema change, not a label change.
- **The public PO pages resolve the order value through `resolveOrderValue(request, invites, invite?)` (`paymentUtils.ts`)** — award → `awardAmount`, else `resolveFinalVendor` (the negotiated GST-inclusive INR total), exactly what `AccountsPanel` shows internally. `request.budget` (the buyer's estimate) survives only as `resolveFinalVendor`'s documented last-resort fallback when the finalized vendor has no quotation; the pages no longer reach it directly, so the PO and every milestone are built on the agreed price.
- **The supplier PI amount pre-fills in INR** (`inrRfqTotal`, not `rfqTotal`) to match its "PI Amount (₹)" label and everything Accounts consume from it (`ProformaInvoice.amount`, TAT delay liability). A foreign vendor additionally sees their own quoted amount, labelled in its own currency.

**INR-basis invariant, part 2 — comparison surfaces + own-currency labels (2026-08).** The same rule applied to every remaining surface that picks a "lowest" or prints a figure under a `₹` label:

- **Comparison helpers are shared and INR-based.** `lowestInrUnitIndex(quotes, lineItemId)` + `quoteLineUnitPrice(quote, id)` in `auctionUtils.ts` decide the per-line **"↓ Lowest"** column in `VendorGrid` (which also steers the award via the Final-Decision auto-fill). `VendorGrid`'s legacy `lowestTotalQuoteId` / Vendor Shortlist ordering and `RfqPanel`'s mobile card `L1` chip + cheapest-first sort all compare `inrQuoteGrandTotal` / `inrRfqTotal`. `exportUtils.buildVendorComparisonRows` (extracted, pure, tested) sorts the Excel export the same way — the sheet's green "lowest" fill is decided there.

- **`RequestQuotationView` compares GST-INCLUSIVE, INR** — it used to mix `inrRfqTotal` (GST-inclusive) with `inrQuoteGrandTotal` (GST-exclusive) and flag the minimum "Lowest" on the **public plant-head approval page**. The card states the basis next to the heading.
- `formatPrice` on `capex/[id]` rounds (its inputs are FX-converted), and `AccountsPanel` reads `resolveOrderValue` instead of inlining `awardAmount ?? 0`.

**INR-basis invariant, part 3 — the award grids swept end to end (2026-08).** Parts 1–2 converted *some* cells in `VendorGrid` / `RfqPanel` and left the rest, so each pass created a fresh on-screen contradiction (a converted line price beside an unconverted column total). Both files were then swept exhaustively — every `₹` literal and every `fmtCurrency(` call classified as *comparison figure* (keep `₹`, ensure the value is converted) or *vendor's own quoted figure* (keep the value, carry its own symbol).

> **That sweep criterion is INSUFFICIENT — read this before sweeping this class again (2026-08).** "Grep every `₹` literal and every `fmtCurrency(` call" structurally cannot find money that renders as a **bare number with no symbol at all**, and that blind spot is why four waves each left a straggler. **A value with no symbol is still a money value, and an unlabelled `<input>` is still a money input.** Sweep by enumerating the money *fields* — every key on `Quote` / `RfqQuote` / `SourcingDecision` / `PurchaseOrder` / `ProformaInvoice` that holds an amount — and then checking, per surface, that each one both *renders* in a stated currency and *prompts* in one; do not grep for a symbol you are hoping is already there. Useful greps for the invisible half: `>{` interpolations of a money key, `placeholder="Enter` / `placeholder="0"`, and `Number(` sums whose result is printed under `₹`.

- **One shared helper, in `currencyUtils.ts`: `inrWithNative(amount, currency)` → `{ inr, native }`** (and `inrWithNativeLabel` for the single-string form `₹85,50,000 ($100,000 USD)`, used in table cells, `<option>` labels and `window.confirm` copy). It takes the **vendor's own-currency** amount and is the only way these grids render money. Its doc comment names the trap: feeding it an already-INR figure (`inrRfqTotal`, `inrQuoteGrandTotal`, `lowestRfqTotal`, `awardUnitPriceInr`) double-converts **silently**, because `toInr(x,'INR')` is the identity. Tested in `currencyUtils.test.ts`.
- **The rule the grids now follow:** every money figure renders **INR-primary with the own-currency figure beneath** (or bracketed). Non-money rows (delivery days, warranty years) are untouched. **Inputs stay native** — they hold what someone types and what is sent to the vendor — and are labelled with `currencySymbol(...)` (`$ price`, `unit $`, `$ Freight`). The **whole Final-Decision column** is the exception and is labelled `₹`: its *price* inputs are stamped in INR by `awardUnitPriceInr`, and its freight / packing / service boxes are typed straight into an INR total (see part 4).
- **`VendorGrid` items grid:** per-line cells (native sub-line now sits under the figure it belongs to, not under the next one), the freight/packing/service attribute rows, the **Total Amount** row, and the manual **offer columns** (which carry their own currency from the Currency row, threaded down as `OfferColView.currency`). Each vendor column now literally adds up: line totals + freight + packing + service = Total Amount, on one basis.
- **`VendorGrid` legacy `AttributeRowGrid`:** the `Item Price / Freight / Packing / Service` rows and the `Total Amount` row (via `quoteGrandTotal`), so the matrix agrees with the Vendor Shortlist directly below it and with the INR-decided `lowestTotalQuoteId` chip. The Final-Decision counter column keeps native inputs (it is sent to the vendor) but shows its **total** on the INR basis of the row it sits in. The email-thread `Unit Price` converts too.
- **`RfqPanel`:** desktop per-line cells (unit / subtotal / GST / line total), the mobile per-line rows, the `ATTR_ROWS` freight/packing/service (rendered on **both** surfaces, hence `inrWithNativeLabel`), the per-line vendor `<option>` labels, and the negotiation-history line for messages that carry an `RfqQuote`. `lowestUnit` became **`lowestUnitInr`** and returns the INR minimum — cells previously compared their raw unit against the winner's *own-currency* unit by equality, so a `$1,00,000` unit and a `₹1,00,000` unit both lit up "↓ Lowest".
- **`RequestQuotationView` captions honestly.** "incl. GST" was unconditional; GST is **0** whenever no line carries an `hsnCode`, and `capex/new` never writes one — only a vendor's RFQ submit does. So the common public-approval case (Digitisation/IT with buyer-seeded quotes) captioned a GST-*exclusive* figure "incl. GST". Each entry now carries `gst` and reads `incl. GST` / `excl. GST`, and the heading only claims "compared GST-inclusive" when some quote actually has GST. The comparison itself was never affected — the basis was uniform either way.
- **Still own-currency-under-`₹`, deliberately:** `NegotiationMessage.counterPrice`/`counterFreight` (legacy thread + the `AttributeRowGrid` "Send Decision" payload) carry **no currency field at all** — a schema change, not a label change. And `RfqPanel`'s desktop grand-total cell reads `inv.rfqQuote?.currency` rather than the live counter-form currency, so the label flickers to the stored currency mid-edit (display-only; the mobile card and `inrGrandTotalOf` already use the form currency).
- **Open, not ratified:** `VendorGrid`'s Final-Decision **currency select** writes `sourcingDecision.currency` while the Final-Decision **prices** in the same column are INR by contract. Nothing reads that field for money (only the supplier `AuctionShell` header label), so no figure is wrong today — but the control contradicts the `Price (₹)` beside it and should either go or start converting. Product call.

**INR-basis invariant, part 4 — the bare-number sites the grep could not see (2026-08).** The three sites the symbol-grep structurally missed, plus the asymmetries parts 1–3 created:

- **`VendorGrid`'s Final-Decision freight / packing / service are INR BY CONTRACT and are now LABELLED, not converted.** The locked cell rendered `{fdAttr[key]}` bare and the editable state was an unlabelled `<input placeholder="Enter freight">` — yet `computeFinalTotal` (`/capex/requests`) and `SourcingDecisionBanner` (`/capex/[id]`) both add all three to per-line award prices that `awardUnitPriceInr` already stamped in INR, then print the sum under `₹`. Converting them would be **wrong**: sourcing types these, so there is no source currency to convert *from*. New pure helper **`formatTypedInr(raw)`** in `currencyUtils.ts` renders a typed INR amount (and returns `null` for empty/non-numeric, so no cell can print `₹NaN` — `SourcingDecision.freight` and friends are free-form strings). The input prompts `₹ freight` — symbol **first**, like the offer columns' `₹ price`, so a narrow sticky column truncating the text cannot clip the unit off the end — and carries an `aria-label` naming the row and the currency, mirroring the sibling `Price (₹)`. Non-money rows (delivery days, warranty years) stay bare.
- **`VendorGrid`'s Total Amount row sums each line through `quoteLineUnitPrice`** — the same per-line resolution the cell above it uses — so a quote priced line-by-line but **missing a key** (a buyer-seeded quote only carries the lines that vendor was quoted for) no longer renders `q.price` in the row while counting it as `0` in the total. The legacy **no-`itemPrices`** branch is retained deliberately: there `q.price` is the whole lump-sum quote, and spreading it across every line through the same fallback would multiply the total by the line count.
- **`RfqPanel` symmetry.** The desktop counter unit input and **both** the desktop and mobile `ATTR_ROWS` money inputs (`money: true` on freight/packing/service) now carry `currencySymbol(form.currency)`, as the mobile unit input already did — fixing one side of a desktop/mobile pair is the exact pattern this sequence has been eliminating. The mobile per-line row renders `unitD.native` under the unit (desktop always did), so the unit is not read as rupees. `lowestUnitInr` reads currency through the new **`currencyOf(inv)`** closure — the live counter form's currency while sourcing is editing that column, the stored quote's otherwise — instead of pairing a **live form** unit with the **stored** currency; `inrGrandTotalOf` and the mobile card now share that helper.
- **Known defect, awaiting a product decision — two "cheapest" vendors can appear on one screen.** On `/capex/[id]` the **Vendor Ranking** table (`Bid Subtotal (₹)`, from `computeVendorRankings` = the bid's **base subtotal**) and `VendorGrid`'s **`Best`** chip (from `lowestTotalQuoteId` = `inrQuoteGrandTotal`, the **whole quote** incl. freight/packing/service) sit on the same scroll and **can name two different vendors as cheapest**. Both figures are INR — the disagreement is one of **basis**, not conversion — and labelling the two bases (part 1) did not stop both from reading as superlatives to whoever is awarding. Behaviour is **deliberately unchanged**: picking one basis is a product call (which is "the cheapest quote" for an award?), and the auction threshold basis rides on the same decision. Do not "fix" one side in isolation.

### Approval remarks at every gate + per-line vendor quotation documents (2026-09)

Two changes, both about making a decision carry the reasoning and the paperwork that produced it.

**Every approver and every sender can now leave a remark, at EVERY gate — including on an APPROVAL.** Previously a remark was only collected on the negative outcomes (the Technical team's send-back / reject, an admin rejection via `window.prompt`), so an approval that came with a condition attached had nowhere to live and the next person in the chain saw only a status change.

- **One append-only trail per entity**, `approvalRemarks?: ApprovalRemark[]` on `CapexRequest`, `BudgetProposal` and `VendorInvite` (the per-vendor gates — tech spec — and each split award's fulfillment gates record against the INVITE). `ApprovalRemark` carries `{ stage, action, by, text, at }`; `ApprovalStage` is one flat key per surface, `ApprovalAction` is `approved | rejected | sent_back | forwarded | sent | noted`.
- **`src/lib/approvalRemarks.ts` is the ONLY place a remark is built, sanitized or appended** (pure, unit-tested). Four of the surfaces are tokenised PUBLIC pages taking free text from an unauthenticated browser, so the text is trimmed, control-stripped and length-capped (`MAX_REMARK_LENGTH` 1000) **here** rather than per page — a boundary enforced per-page is one that is eventually forgotten on one page. The trail is bounded at `MAX_REMARKS_PER_ENTITY` (60), dropping the OLDEST. `buildApprovalRemark` returns **`null`** for empty text and `remarkPatch` then returns an **empty object**, so a decision taken with nothing typed leaves the field untouched rather than storing a blank entry or churning React identity.
- **A remark never changes what the workflow does** — it is deliberately not a second status field. The one place it feeds a behavioural field is `decideRequestPlantHead`, where a rejection's remark also becomes the `rejectionReason` the requester reads (it was previously always the placeholder "Rejected by plant head").
- **Optional to approve, REQUIRED to reject / send back.** Every surface disables the negative action until something is typed, and says why. `window.prompt` is gone from `/capex/budget-approvals` (both the budget-proposal and the ad-hoc-transfer rejections) in favour of an inline `RemarkField` panel — the prompt was cancellable into a silent no-op, unstyleable, unvalidatable, and a native modal that blocks the page. The public approve page's `window.confirm` guards went with them: a required reason is a stronger gate than a confirm.
- **Surfaces that COLLECT one:** plant-head request approve/reject and budget approve/reject (`/approve/[token]`), the Global-Accounts budget sign-off (same page, accounts stage), the Technical team's approve / send-back / reject (`/tech-spec/[token]`), sourcing's covering note when it SENDS a spec (`sendTechSpecForApproval` — the sender, not just the approver), Plant Accounts' FA-code handoff and each payment tick (`/po/[token]`), Global Accounts issuing the PO (`/po-issue/[token]`), and the super admin's budget + ad-hoc decisions. `BudgetEditForwardPanel`'s existing note box now routes through the same `RemarkField`.
- **Surfaces that SHOW the trail:** `RemarkTrail` (newest-first, renders **nothing** when empty unless given an `emptyNote`) on the internal request detail (**merging the request's trail with every invite's**, sorted by timestamp, so a reader need not know which entity a gate hung off), inside the expanded budget breakdown on `/capex/budget-approvals`, on both public accounts pages (`orderRemarks` merges request + award), and on `/approve/[token]` — the Global-Accounts signatory would otherwise decide on the numbers alone.
- **The tech-spec page's trail is SCOPED to `stage: 'technical_spec'`, and that is a confidentiality decision, not a filter for tidiness.** That page withholds the vendor's identity by design; the invite's trail also carries sourcing's and Accounts' remarks, written by people who name the vendor freely. It shows only the remarks the page itself produced. Sourcing's covering note still reaches the team through `spec.notes`, the one field they are explicitly told to keep vendor-free.
- Plant Accounts' FA remark **also rides in the handoff email body** — the recipient reads the email, not the audit trail.
- `TechSpecPanel` now renders `spec.decisionNote` for an **approval** too (emerald), not only send-back/reject: hiding a condition on the one outcome that unblocks the award is exactly backwards.
- Shared actor-name constants (`PLANT_HEAD_ACTOR`, `PLANT_ACCOUNTS_ACTOR`, `GLOBAL_ACCOUNTS_ACTOR`, `TECHNICAL_TEAM_ACTOR`) moved into `constants.ts`. The same string is now written from two sides — the page stamps the status-history actor, `capexContext` stamps the remark author — and a page-local literal drifting from the context's would split one person's actions into two names in the audit trail.

**The vendor attaches a supporting document to EACH LINE ITEM of their quotation.** One undifferentiated quote-level attachment could not say which datasheet belonged to which machine.

- `RfqQuote.lineDocuments?` / `Quote.lineDocuments?`: `Record<CapexLineItem['id'], QuoteLineDocument>`. Base64 is offloaded to IndexedDB under **`qdoc:<id>`** by `stripInviteFiles`/`hydrateInviteFiles`, which handle **all three places one map can be referenced** — the live `rfqQuote`, an auction `Quote`, and the frozen copies inside `rfqThread` (factored into `stripLineDocuments`/`hydrateLineDocuments`; a fix applied to two of three copies is how a blob goes missing). Nothing may assume `base64` is populated: metadata loads first and the payload merges back asynchronously, so **every render path tolerates an empty `base64` by showing the filename WITHOUT a link** rather than an anchor that downloads nothing.
- **`src/lib/quoteDocuments.ts`** (pure, unit-tested) owns the cap (`MAX_LINE_DOC_BYTES` = 500 KB, matching the portal's existing attachment limit), the accepted types, `readQuoteLineDocument` (resolves an `error` rather than throwing), and **`sanitizeLineDocuments(raw, allowedItemIds?)`** — called at both public mutation boundaries (`proposeRfqQuote`, `submitQuote`), which drops any key that is not a line item on that request. It deliberately **KEEPS an entry whose `base64` is `''`**: that is a stored-and-stripped document, and deleting it would destroy the vendor's paperwork the first time sourcing re-sanitizes a quote.
- **Who owns the map decides what an ABSENT map means, and it is keyed on `by`, not on emptiness.** SOURCING has no upload control at all (their counter is built from price fields alone by `quoteFromForm`), so an absent map means "not specified" and the vendor's documents are carried forward — otherwise countering a price would silently delete the datasheets the tech-spec gate and the approver's quotation view both read. The SUPPLIER owns their own paperwork and has a control per line, so **their map is authoritative including when it is empty** — a vendor who removes their last attachment must actually see it gone. An auction re-bid that attaches nothing likewise keeps what is on file.
- **UI:** `LineDocumentCell` is ONE implementation shared by the desktop table (`SupplierQuoteTable`, new trailing `Document` column) and the mobile cards (`SupplierQuoteCards`, new row) — this codebase has repeatedly shipped a desktop/mobile pair where one half got a fix. The column appears when the vendor can upload OR when a stored quote actually carries documents, so a read surface with no attachments keeps the old 7-column layout instead of a column of dashes; read mode falls back to `quote.lineDocuments` so every read surface in the portal picks it up without threading a prop. Wired into the RFQ entry form, the vendor's counter form (seeded from the quote on the table, with a compact per-line list) and the auction bid form (seeded from the stored bid). Internally, `QuoteLineDocLink` renders the download chip in `RfqPanel` (desktop cell + mobile card), `VendorGrid`'s per-line cell (reading the bid, falling back to `rfqQuote` for an escalated RFQ) and `RequestQuotationView` — so the plant head approving by email sees the datasheet behind the price.
- **Bug fixed in passing: `sanitizeRfqQuote` was DROPPING `deliveryDays`.** The RFQ form collects it as a required field and `deliveryLeadDays` (`paymentUtils`) reads it to date the final payment, but the sanitizer's whitelist carried only the legacy `deliveryWeeks` — so every RFQ quotation lost its lead time on the way in and the expected-final-payment date fell back to a field that is usually absent. Both are carried now.

Regression tests: `src/lib/approvalRemarks.test.ts`, `src/lib/quoteDocuments.test.ts` (`npm test` is now 431 tests across 20 files).

### Green Field budget planning — site on master, budget by maintenance, full approval chain (2026-09)

**Budget Planning (`/capex/budget-proposals`) opens on a TWO-CARD chooser — Green Field first, then Brown Field — and nothing else renders until one is picked.** `fieldType` starts `null`; the header then reads `Budget Planning · <type>` with a **Change** control back to the cards. The old grey "Budget type" pill row is gone: a one-at-a-time choice is a step, not a toggle buried in the scope line, which is how that pill group went unnoticed twice. **A role only ever sees cards it can author** — `GREEN_FIELD_ROLES` is `maintenance` + `super_admin` (maintenance authors the new site's budget, the admin keeps access to review and re-publish a year), so `sourcing_member` sees the Brown Field card alone rather than a locked dead end. A role switch away from Green Field rights **returns to the card step** (and clears the plant + open draft) rather than silently re-pointing them at another budget.

**Green Field runs the SAME approval chain as Brown Field: Plant Head → Admin → Global Accounts.** The direct-publish shortcut (`publishGreenFieldBudget`, `publishesDirectly`) is **removed** — it was only ever defensible while the super admin was both author and approver, and the author is now `maintenance`, who is not an approving authority. `submitBudgetProposal` handles both field types identically (`pending_plant_head`, token minted), and the editor's button reads **Submit to Plant Head** for both. `/capex/budget-approvals` and the public `/approve/[token]` page need no field-type filtering — neither scopes by field type — but both now **name the envelope** (`Green Field · <plant> · …`, `FY 2026-27 Green Field Budget`, and a `Budget:` line in the accounts email), because "which budget am I signing?" must never be inferred from the line items.

**`publishProposalToMaster(target)` in `capexContext.tsx` is the ONE path from a proposal to a live budget**, called from `decideBudgetAccounts` at the final gate. Brown Field appends rows, exactly as before. Green Field does two extra things — and `decideBudgetAccounts` did **neither** before this change, so routing Green Field through the chain without them would have published a budget with no envelopes and doubled the plant on every re-publish:
- **It writes the plant / section / head envelopes** (`buildGreenFieldAllocationsFromProposal`), without which every Green Field screen renders the plant as having no allocation at all.
- **Republishing the same `plant + targetFy + projectType` REPLACES that scope** in `capexMaster` and in all three allocation arrays, instead of appending — a corrected re-upload must not leave the old lines beside the new ones and double the plant's budget.

It takes the proposal **by value**: `decideBudgetAccounts` resolves the target from committed state before mutating, so the publish never depends on a `setState` updater having run first. The editor still validates its own LIVE draft (`validateProposal(next)` in the page) before submitting, because a save-then-submit in one click would otherwise validate the pre-save copy.

**One upload assigns budget at EVERY level of the hierarchy.** A Green Field budget is a tree (plant → section → head/shop → per-machine), and the template carries it on a flat sheet by **repeating each envelope figure on every row of its scope**: `S.No | Plant Budget (Cr) | Section | Section Budget (Cr) | Head | Head Budget (Cr) | Department | Sub Particulars | Qty | Total Cost (Cr) | Reason | Benefits | ROI`, plus a **Sections & Heads reference sheet** so a typo in Section is avoidable. The importer takes the **first non-empty value per scope** and ignores the repeats (`summarizeProposalGreenField`); where the sheet carries no envelope for a scope, it **rolls up from its children** — a budget that adds up beats a zero envelope that would render every head as "over allocation". `downloadImportTemplate(source, fieldType)` branches to the Green Field sheet; its worked examples are internally consistent (machines sum to head, heads to section, sections to plant = ₹55 Cr) so the shape is never ambiguous.

**Section is a CLOSED list, enforced in `validateProposal`, not just the UI.** A free-text section would silently file the machine under an envelope `/capex/new` never renders — the request wizard reads sections from `GREEN_FIELD_SECTION_ORDER` — so a row whose `division` is not one of the four is rejected at submit. The editor's Section cell is a `<select>` for the same reason.

**Type/util changes:** `BudgetProposal.fieldType?: FieldType` (absent ⇒ `brown_field`; every pre-existing proposal is Brown Field, so the fallback is not a guess) + `plantBudgetCr?`; `BudgetProposalItem.sectionBudgetCr?` / `headBudgetCr?` (per-SCOPE figures, not per-row); `ParsedMasterRow` gains `division` / `plantBudgetCr` / `sectionBudgetCr` / `headBudgetCr`; `PlantMeta.greenFieldFy?` records the FY a site was registered for. New helpers in `budgetProposalUtils.ts`: `proposalFieldType`, `getLatestFyForProposal` (field-scoped — a published Brown Field year must never move the Green Field one), `currentFyCode`, `summarizeProposalGreenField`, `greenFieldPlantBudgetCr`, `buildGreenFieldAllocationsFromProposal`. `buildMasterItemsFromProposal` now honours `proposal.fieldType` instead of hardcoding `brown_field`. **FY defaults differ by field type:** Brown Field plans the year AFTER the live one (`nextFyCode`); Green Field opens the plant's budget for the FY the site was registered for (`PlantMeta.greenFieldFy`), falling back to the **current** year, because a new plant has no prior Green Field year to roll forward from.

**The seeded Green Field budget is REMOVED (`GREEN_FIELD_BUDGET_CLEAR_V1 = 'gf_budget_cleared_v2'`, `mockData.ts`).** `greenFieldSeedMaster` is now `[]` — the seed is retired, nothing is seeded and nothing is backfilled, exactly as the cleared Brown Field FY already works. On load, a browser holding the old demo budget has **every Green Field master row AND all three `greenFieldBudgetAllocations` arrays wiped once**, in the same pass: keeping the envelopes would leave a plant/section/head budget describing line items that no longer exist, which every Green Field screen renders as a fully-unspent allocation. Bump the constant to re-run the wipe. **Only Green Field is touched** — Brown Field, Digitisation, IT, vendors, plants and workflow data all load normally.

**A Green Field site can be registered from EITHER screen — CAPEX Master or Budget Planning — and its BUDGET is always authored in Budget Planning.** Both entry points open the same **`src/components/CreateGreenFieldPlantModal.tsx`**: one validated implementation, extracted precisely so two screens offering one action cannot drift apart. - **Budget Planning** (`GREEN_FIELD_ROLES` — `maintenance` + `super_admin`): registers the site, **selects it and drops straight into its blank budget draft** without leaving the page — an author already on the funding screen must not be bounced to another route to create the plant they are about to fund. Key invariants — each exists because getting it wrong once already produced a bug during review:

- **`requestValue(request, reqInvites, index)` is the single source of a request's money figure**, returning a `ValueBasis` (`awarded` → `approved` → `quoted` → `estimated` → `allocated` → `none`) that is rendered as a caption next to the figure **wherever the figure is a single request's value** — a number whose provenance is invisible is worse than no number. Never inline a different fallback chain. **Carve-out:** aggregates that sum `requestValue` across many requests (e.g. the Administration Portfolio FY table's Committed / Awarded / Paid columns) have no single basis to caption and deliberately omit one — this is not an oversight to "fix".
- **A KPI tile's number and its destination list's count MUST agree — this is a contract, not a nicety.** Two rules make it hold, and both were earned by a real defect this run:
  - **A PREDICATE tile's route carries the same predicate, threshold included.** "Stuck at plant head" counts requests past `SLA_DAYS.plantHead`, so it routes to `?metric=stuck_plant_head`, **not** `?filter=pending_head_approval` — the old status-only route made a tile reading 2 land on a list of 11 with nothing marking the 2. The tile and the route derive from **one exported helper** (`stuckAtPlantHead`, imported by both `adminQueues` and `kpiRoutes`); **never re-implement a threshold inside a page.**
  - **A COHORT-MEDIAN tile routes to ITS OWN SAMPLE, and the destination MUST show `stillOpen`.** A median is not a filter, so the destination is the cohort the median was measured over — and because a median over *completed* work is survivorship-biased, the page states the still-running count **in words**. This is the rule most likely to be silently broken by a future edit, and the failure is the worst kind: **a median over finished work reads FASTEST exactly when the most work is stuck**, because the stuck rows are the ones excluded. Hiding `stillOpen` turns a paralysed pipeline into a green number. `stageDaySample` / `inviteLegSample` return a 4-state membership (`not_reached`/`not_started` → `open` → `sampled` → `dropped`) precisely so the list and the median can never disagree about who is in the cohort.
- **The two `createdBy` conventions on `CapexRequest` vs `BudgetProposal` are NOT the same field semantics, and confusing them renders a dashboard that is permanently, silently empty.** `CapexRequest.createdBy` is stamped as a **display name** — `ROLE_NAMES[currentRole] ?? currentRole` at `capex/new/page.tsx:985` — so `BuyerDashboard` scopes on `r.createdBy === ROLE_NAMES[role]`. `BudgetProposal.createdBy` is stamped as the **raw role key** — `createdBy: role` at `capex/budget-proposals/page.tsx:93` — so `MaintenanceDashboard` scopes on `p.createdBy === 'maintenance'` directly, with no `ROLE_NAMES` lookup. Swapping the two conventions doesn't error; it just shows the "nothing yet" empty state forever, indistinguishable from a legitimate clean slate. Check which entity a filter is scoping before writing `createdBy ===`.
- **FY attribution:** a request belongs to the FY of its linked master rows (`kpiPortfolio.requestFy`), else the live FY of its **own field type** (`getLatestMasterFyForField`). Field types are never mixed — the old dashboard compared a Green Field FY allocation against Brown Field commitments.
- **NEVER DIVIDE ACROSS FIELD TYPES. Each field type is its own budget envelope.** Summing money across field types is fine — rupees add. A **ratio** of those sums is not, because `Σcommitted ÷ Σallocated` can put one field type's commitment over another field type's budget. The FY-attribution invariant above did **not** prevent this: `AdminDashboard`'s hero utilisation line divided Brown Field committed by Green Field allocation on today's data (Brown Field FY 2026-27 ships empty, so the only allocation in the portfolio was Green Field's) and printed a confident, meaningless percentage. Utilisation is computed **per envelope** (`fyBudgetPosition` returns one position per field type; the hero states how many field types are funded instead of blending them). Any new portfolio ratio must state which single envelope it is over, or not be a ratio.
- **Two boundary conventions exist, both correct, and they are NOT the same rule — do not "unify" them.** `agingBuckets` (`kpiUtils.ts`) uses an **exclusive upper bound**: an age of exactly 3 falls in `3-7`, exactly 7 falls in `7-14` — the boundary belongs to the **older** bucket, the standard aging-report convention (a value only graduates once it has fully completed the younger span). `itemBreached` (`kpiQueues.ts`) uses **strictly greater than**: an age of exactly `SLA_DAYS[slaKey]` is **inside** the threshold, i.e. **compliant, not breached**. So an item can sit in the `7-14` bucket while not being breached at a 7-day SLA, and that is right. Writing one sentence that claims a single rule would be a documented lie about half the codebase and would invite an editor to "fix" correct code. Each convention has exactly one implementation and every caller goes through it (`bucketForAge` asks `agingBuckets` about a single-element array rather than re-deriving; `queueHeadline` and `buildBucket` both call `itemBreached`).
- **`fyBudgetPosition` — and therefore the Admin dashboard's Portfolio FY table — uses ONE global latest FY per field type.** Plants publish next-FY Brown Field budgets independently, so on a portfolio where plants have diverged, this **silently omits every plant still sitting on an earlier FY** for that field type; the FY column names the year being shown, which is the only cue this is happening. This is a **deliberate scope decision, not an oversight**.
- **Over-allocation exposure is the one figure that scopes per plant instead.** `AdminDashboard`'s "Over-allocation exposure" tile does **not** go through `fyBudgetPosition`'s single global FY — because different plants publish next-FY budgets independently, it builds its own `plant → that plant's latest Brown Field FY` map inline, then calls `headPositions` once per `(plant, fy, projectType)` scope. A global "latest FY" here would silently drop every over-budget head for a plant still on an earlier year the moment any other plant published a newer one — exactly the failure this tile exists to catch. When adding a new portfolio-level figure, decide explicitly whether it needs this per-plant treatment or can live with the FY table's global-latest limitation.
- **Savings only exist once a request is `awarded`/`approved`** (`savingsForRequest` returns `null` otherwise — a live quote in progress is not a saving). Split-award negotiation savings restrict both sides of the comparison to `awardedItemIds` via `linePrices` and exclude freight/packing/service, matching `buildAwardGroups`'s basis for `awardAmount`.
- **Head-level figures use `usedAmountByMasterItemId` + `effectiveHeadAllocationCr`**, the same source `/capex/master` uses, so the two screens can never disagree. Labelled **"committed (est.)"** in the UI — it's an estimate basis, not a settled figure.
- **`SLA_DAYS` in `kpiUtils.ts` are placeholders**, not measured SLAs — one const to change when a real policy exists.
- **FLOW metrics are derived; STOCK metrics are MEASURED FORWARD, never reconstructed.** Requests raised / awarded / completed per month are historical facts already on the record (`createdAt` + `statusHistory`), so `kpiTrends.ts` derives them for any past month. Allocation / commitment / utilisation / over-exposure / open sourcing load are **stocks** with no such record — what a plant's budget *was* last month is genuinely unknowable — so `kpiSnapshots.ts` writes one measured record per (day, field type, plant) on load and every chart states its own `measuredFrom` date. **Gaps are not zeros** and a metric added later is ABSENT from older records, never `0`; there is no backfill, by design.
- **The contract is `measured only, labelled` — and it is enforced by construction, not by discipline.** `snapshotSeries` never interpolates, zero-fills or carries a value forward across an unmeasured day; `measuredFrom()` returns the earliest measured date so a chart can **label its own horizon** rather than let a short history read as a decline. `MeasuredSeriesChart` renders **one `<path>` per contiguous run of measured days**, so a gap is a visible break in the line *because there is no geometry spanning it* — it cannot silently regress to a smoothed line the way a single-path chart with a fill-forward would. History therefore starts thin and thickens with use, and a sparse chart on a fresh store is the **correct** output, not a bug to seed around.
- **`liveFyByPlant` (`kpiPlants.ts`) is per-plant BY NECESSITY, and is the only implementation of that rule.** Plants publish next-FY budgets independently, so a single global "latest FY" makes a plant that is merely **out of scope for that year** read as a plant that is **under-spending** — a wrong number, not a missing one. `latestMasterFyForPlantField` is a lookup over the same map; `plantKpis`, the plant comparison and `plantHeadUtilisation` all call `liveFyByPlant` once rather than re-deriving per row. (The Portfolio FY table's global-latest scoping, two bullets above, is the documented exception and is captioned as such.)
- **Snapshot retention is 90 days (`SNAPSHOT_RETENTION_DAYS`), and retention is the lever — not the size ceiling.** The payload shares the ~5 MB `localStorage` quota that `fileStore.ts`'s IndexedDB blob-offload exists to protect. At 180 days the seeded worst case measured **2,013,841 chars ≈ 1.92 MiB (~38% of quota)**; at 90 it is **1,006,921 chars ≈ 0.96 MiB (~19%)**. Snapshots are *derived observational* data that can be re-measured tomorrow; `requests`/`invites` in the same payload are the **irreplaceable primary record**, so the derived series yields. `kpiSnapshots.test.ts` asserts an absolute ceiling (1,700,000) **and** a per-record ceiling (291 chars — the canary that catches a new FIELD, which cutting retention would not pay for).

**Honest KPI routes — `/capex/requests` filters (2026-08).** A tile that links to a list must land on **the rows its own number counts**. `/capex/requests` used to support one param, `?filter=<status>` (single status equality), which is too weak for that: "Stuck at plant head" counted only requests past the `SLA_DAYS.plantHead` age and routed to `?filter=pending_head_approval`, so a tile reading 2 landed on a list of 11 with nothing marking the 2; five Sourcing duration tiles all routed to the bare list. The registry now lives in **`src/lib/kpiRoutes.ts`** (pure, unit-tested) and the page consumes it.

- **Three card kinds, three destinations.** **Predicate** count → the route carries the whole predicate, **age threshold included** (`?metric=stuck_plant_head`). **Cohort median** → a median is not a filter, so the destination is **the sample it was measured over**, and the page states the `stillOpen` count in words (a median over finished work only is survivorship-biased; hiding the still-running rows is what makes a cycle time look faster than it is). **Ratio** → the **denominator** with the numerator marked per row, so both halves of the fraction stay visible.
- **Metric keys** → tiles: `my_requests` (Buyer), `stuck_plant_head` + `rejection_rate` (Admin), `sourcing_cycle`, `vendor_participation`, `invite_first_quote`, `first_quote_agreed`, `tech_spec_gate` (Sourcing). **`metricHref(key, plant?)` builds every href** — the dashboards never hand-write the query string. The Maintenance tiles point at `/capex/budget-proposals` (budget proposals are not requests) and are untouched.
- **The plant lens rides in the SAME builder (2026-08).** `metricHref`'s optional second argument appends `?plant=`, so a plant-scoped tile lands on a plant-scoped list. - **The predicates ARE the tiles' derivations, imported not re-implemented.** `stuckAtPlantHead` was extracted from `adminQueues` (which now calls it); **`stageDaySample`** was extracted from `medianStageDays`/`stageDaysPercentiles`' shared traversal; **`inviteLegSample(invite, leg)`** + **`inviteHasQuote`** were extracted from `sourcingPerformance` (which now calls them). (legacy only: negotiation → sourcing_approved → buyer_approved; new auctions skip these)

After `sourcing`, a Brown Field request is **RFQ by default** (`CapexRequest.sourcingMode`: defaults to `rfq`, no chooser); a reverse `auction` can only be **escalated from RFQ** (requires ≥2 vendor quotes — see RFQ section). **Both paths converge identically at `pi_requested` and run the same fulfillment chain from there.** The auction ends via the countdown reaching `endsAt` **or** sourcing clicking **Close Auction Now**. After it ends, `sourcing_head`/`super_admin` **awards line items to vendors** in the grid's per-line **Final Decision** column (a winning vendor + final price per line) and clicks **Approve Final Decision & Award** — this is a **split award** that can hand different line items to different vendors, creating one **award** per winning vendor (`finalizeSplitAward`). **Each award is its own fulfillment track** (PI → contract-terms approval → PO → payments) carried on that vendor's `VendorInvite` (see **Split award (multi-vendor reverse auction)** below). The vendors already approved the pre-bid **Business Rules** (Commercial Terms / PBG / DLC) to participate, so there is **no post-award terms step** — sourcing clicks **Request PI** for that award directly (`requestProformaInvoice`, restricted to `sourcing_head`/`super_admin`). Each awarded vendor uploads its own Proforma Invoice, then **Plant Accounts** assign that award's FA codes and later its milestone payments while **Global Accounts ("Satish")** issue its PO — each on their own emailed public link; the **request** is `completed` only when **every** award completes. (RFQ + legacy single-vendor auctions keep the single-vendor request-level chain: one Request PI → one `pi_submitted` → FA → PO → payments → `completed`.) New statuses (`pi_requested`, `pi_submitted`, `accounts_processing`, `payment_in_progress`, `completed`) are added to `CapexStatus`, `CAPEX_STATUS_FLOW`, `ALLOWED_TRANSITIONS`, `STATUS_COLORS`/`STATUS_LABELS`, and `STATUS_TO_STEP`. The `sourcing_approved` / `buyer_approved` statuses are retained only for legacy/in-flight requests created before the buyer step was dropped; `ALLOWED_TRANSITIONS` keeps `negotiation → pi_requested` and `sourcing_approved → pi_requested` so those legacy requests can still reach fulfillment.

`initialStatusForRequest` in `capexContext.tsx` routes new submissions by field type: Green Field, Digitisation, and Information Technology start directly in `sourcing` (no plant-head approval); Brown Field starts in `pending_head_approval`. The `ALLOWED_TRANSITIONS` map still permits `submitted → sourcing` explicitly. The `CapexProvider` enforces transitions via this map — `updateRequest` rejects invalid transitions with a console error and returns the unchanged request.

### State management

`CapexProvider` (`src/lib/capexContext.tsx`) is the single source of truth, mounted in both `(internal)/layout.tsx` and `(public)/layout.tsx`. It exposes:

- `requests`, `vendors`, `invites`, `chatMessages`, `plants`, `categories` — domain arrays
- `capexMaster` — `CapexMasterItem[]` for per-plant/FY budget planning (fields: `id`, `fieldType`, `projectType?` (`rac` | `ems` | `component` | `fan` for Brown/Green Field; defaults to `rac` on load), `plant`, `fy`, `head`, `department`, `subParticulars`, `rate`, `totalCost`; optional Brown Field workbook fields: `sNo`, `rateRs`, `qty`, `reasonForRequirement`, `benefits`, `roi`); `qty` is editable on `/capex/master` only — not shown on request line items; `fieldType` is `green_field` | `brown_field` | `digitisation` | `information_technology` (defaults to `brown_field` on load); `cloneMasterForFY` seeds a new fiscal year from the latest
- `usedCrMap` / `getUsedCr(plant)` — derived budget consumption per plant (in Crore), computed via `useMemo` over non-rejected requests
- `usedAmountByMasterItemId` — per master line-item budget consumed (INR), from non-rejected requests linked via `masterItemId` or `lineItems[].masterItemId`; drives red overrun indicators on `/capex/master`
- `setAuctionConfig(requestId, config)` — writes `CapexRequest.auctionConfig` for reverse auction timing and threshold
- `inviteVendors(requestId, vendorIds[])` — creates `VendorInvite` records with unique tokens for the supplier portal; called automatically when auction starts with selected vendors
- `CapexRequest.lineItems?: CapexLineItem[]` — sub-items from the multi-row grid; each `CapexLineItem` carries its own `masterItemId?`, `masterHead?`, `division?` (Brown Field flat bucket or Green Field section name), `machineCapacity?` (free text, Machinery head rows), `description`, `category`, `quantity`, `uom?`, `specs?`, `budget?`, `remarks?`, `vendorRecommendation?`, optional attachment (base64), and `lastPrice?`/`lastVendor?` (historical pricing shown in the grid for reference)
- `CapexRequest.masterItemId` — optional link to a `CapexMasterItem` (copied from the first line item); the `/capex/master` page uses this to show which requests are associated with each budget line item
- `CapexRequest.statusHistory` — append-only log of `{ status, actor, at }` entries; `updateRequest` pushes an entry on every valid transition
- `CapexRequest.fieldType?: FieldType` — `green_field`, `brown_field`, `digitisation`, or `information_technology`; chosen before the new-request wizard
- `CapexRequest.projectType?: ProjectType` — RAC/EMS/Component/Fan business category for Brown and Green Field; scopes master lookups (`greenFieldProjectType` kept as legacy alias)
- `CapexRequest.greenFieldPlantCreation?` — legacy payload when a Green Field request created a plant inline (deprecated; plant creation is on master)
- `CapexRequest.auctionConfig?: AuctionConfig` — reverse auction: `startedAt`, `durationDays`, `endsAt`, optional `threshold` (INR); lifecycle tracked by timestamps, not status transitions
- `CapexRequest.sourcingDecision?: SourcingDecision` — written by the sourcing flow; holds `selectedVendorId`, `finalPrices` per line item, `freight`/`packing`/`service`/`delivery`/`warranty`, `currency`, `offerCols` (multi-vendor comparison matrix), and `finalVendorPerItem` (per-line-item vendor selection)
- `masterHeads: string[]` — user-created custom budget heads; persisted in `capex_data_v2`; mutations: `addMasterHead`, `renameMasterHead`, `removeMasterHead`
- `addMasterItem(item)` / `updateMasterItem(id, updates)` — add or edit a `CapexMasterItem` row on the master page
- `customPlants: PlantMeta[]` — plants added by users beyond the seeded `PLANTS` list; `PlantMeta.greenFieldPlant?` marks Green Field plants; mutations: `addCustomPlant`, `createGreenFieldPlant` (metadata + optional plant budget envelope)
- `greenFieldBudgetAllocations: GreenFieldBudgetAllocations` — Green Field-only plant, section, and head budget envelopes (`plantBudgets`, `sectionBudgets`, `headBudgets`) scoped by `fy + projectType + plant`; persisted in `capex_data_v2`; mutations: `setGreenFieldPlantBudget`, `setGreenFieldSectionBudget`, `setGreenFieldHeadBudget`; `createGreenFieldPlant` seeds plant budget when `budgetCr` is provided; `cloneMasterForFY` clones allocation rows with master items
- `kpiSnapshots: KpiSnapshot[]` — the MEASURED daily stock-metric history (see `kpiSnapshots.ts`). **Read-only on the context — there is deliberately no exposed mutation**, because a caller able to write a snapshot could write a value for a day it did not measure, which is the one thing the whole module exists to refuse. The **only writer is the provider's own once-a-day capture effect**, which calls `buildSnapshots` + `mergeSnapshots` (keyed on date + field type + plant, so a same-day re-run replaces rather than appends). The cross-tab `storage` listener deliberately does **not** re-sync it.
- `resetData()` — clears all localStorage and redirects to `/login`

On mount, the provider seeds from `mockData.ts` if `localStorage` is empty. A `storage` event listener re-syncs `invites` when the supplier portal (a separate browser tab) submits a quote. If localStorage already contains `capexMaster` data, the provider backfills missing **Green Field** seed rows only (matched by backfill key including `projectType`). Brown Field rows are replaced once when `brownfieldSeedVersion` in storage differs from `BROWNFIELD_SEED_VERSION` in `brownFieldSeedData.ts` (currently `fy2026_27_cleared` with an empty seed — FY 2026-27 is authored from Budget Planning). Digitization-head Brown Field rows migrate to `digitisation` field type once when `digitisationMigrationVersion` differs from `DIGITISATION_MIGRATION_V1`. Brown Field master rows are flattened to `FLAT_MASTER_DIVISION` (`Other Brown Field`, internal only) once when `flatMasterMigrationVersion` differs from `FLAT_MASTER_MIGRATION_V1`. Green Field rows migrate to section structure (`Plant Machinery`, `Utilities`, `Compliances`, `Information Technology`) once when `greenFieldSectionMigrationVersion` differs from `GREEN_FIELD_SECTION_MIGRATION_V1` in `greenFieldConstants.ts`. Stored master rows are migrated on load via `normalizeMasterItemDivision` in `greenFieldConstants.ts`.

- `Quote.seededByBuyer?` — true when the buyer entered the quote during request creation (shown as “Added at request” in `VendorGrid`)

The supplier portal (`/supplier/[token]`) resolves an invite from the URL token via `resolveInviteByToken` in `src/lib/tokenUtils.ts`. Layout is a modern auction bid screen: sticky header (request no, countdown, vendor identity, currency), rank + best price + your bid summary card, collapsible auction rules and request details, bid-entry table (line items with unit price, total, per-line best price only — no anonymous vendor labels), additional-charges panel, delivery/validity/supporting-info section, and a sticky bottom submit bar (rank hint, reset, submit). Supplier quote attachments are capped at 500 KB; base64 is stored inline on the `Quote` object. Reverse-auction re-bids overwrite the single stored quote (`submitQuote` replaces `quotes[0]`). Ranking, gap-to-best-price, threshold warnings, and countdown use helpers in `src/lib/auctionUtils.ts`.

**Responsive (two distinct UIs).** Every supplier-portal state renders cleanly on **desktop** and **mobile (~390px)**. The **pricing** screens (RFQ quotation entry, read-only quote summaries, and the auction bid) present line-item pricing as a **desktop table that mirrors the internal sourcing grid** (`SupplierQuoteTable` — near-black `#171717` header, line items as rows: `# / Description / Qty / UOM / HSN-GST / Unit Price / Line Total`, attribute rows, `#F4F4F5` grand-total row with "incl. ₹X GST") via `hidden lg:block`, and a **mobile card stack** (`SupplierQuoteCards`) via `lg:hidden`. Both share one `variant` API (`read`/`entry`/`bid`) and compute GST + grand total through `rfqUtils` (`rfqTotal`/`rfqGstAmount`), so desktop and mobile never diverge; **all** read surfaces (under-review, counter, agreed, approved, rejected) route through the same line-item-aware summary (`RfqQuoteSummary`, which falls back to the legacy lump-sum `QuoteSummaryCard` only when a request has no line items). The reverse-auction **threshold is surfaced once** (bid-entry header chip + rank summary), never per line — but **which basis it is measured against is an OPEN question, not a settled rule.** Three things currently disagree: the threshold field on the auction setup **pre-fills from `lowestRfqTotal`, a whole-quote GST-inclusive figure**; the supplier screen **compares it against the bid SUBTOTAL** (`itemSubtotalInr`, see the `aboveThreshold` comment in `supplier/[token]/page.tsx` and the INR-basis note above); and the auction **best price** is whole-quote. So a threshold seeded from one basis is enforced on another, and on one screen the rank table's L1 (subtotal) can name a different vendor from the grid's "Best" chip (whole quote). Both figures are INR — this is not a currency defect — and the behaviour is **deliberately left alone pending a product decision**. Do not "fix" it by converting one side; pick a basis and align the pre-fill, the comparison and the label together. Non-pricing states (auction-approval pending/waiting/declined/ineligible, closed, invalid, PI upload, fulfillment/PO/payments, INCO gate) use the shared public hero card `SUPPLIER_CARD` (`uiTokens.ts`) with action-button rows that stack on mobile (`flex-col sm:flex-row`).

### UI stack

- Tailwind v4 (PostCSS plugin — no `tailwind.config`; theme tokens defined in `globals.css`)
- **Theme:** **black-and-white chrome** — white surfaces (`--background`/`--card`), near-black foreground (`--foreground`, `#171717`), **blue `#2563EB` as the single chrome accent** (`--primary`; CTAs, focus, interactive emphasis), and **red reserved for danger** (destructive/over-budget). Page chrome, tables, buttons, cards, sidebar and nav are grayscale + blue (+ red for danger); `slate-*` is the neutral. Subtle charcoal→black gradients in appropriate places (login hero, table headers). **Two colour exceptions on top of the B&W chrome:** (1) **status badges carry colour** (see below) for workflow visibility; (2) **value semantics** — the **lowest quote / "best price"** highlight and any **savings / under-budget** indicator render **green** (`emerald-*` — comparison-grid lowest cell + `↓ Lowest`/`L1`/`Best` chips, dashboard Money-Saved + Negotiated-Savings + Remaining, Saved-vs-Budget card, "under allocation" chip, supplier Best-Price), while any **loss / over-budget** indicator renders **red** (over-budget chip, "over allocation", Over-Budget card). ### Reverse auction approval document (pre-auction vendor confirmation)

Before an auction starts, the sourcing team must generate a "Business Rules for Reverse Auction" document and send it to shortlisted vendors for approval. Vendors must approve their participation before they can bid.

**Document structure (`AuctionApprovalDocument` in `types.ts`):**
- Generated document ID, timestamps (`generatedAt`, `sentAt`)
- Auction dates/times: `auctionDate`, `auctionOpeningTime`, `auctionClosingTime`
- Bidder acceptance deadline: `bidderAcceptanceDeadlineDate`, `bidderAcceptanceDeadlineTime`
- Vendor revert deadline: `vendorRevertDeadlineAt`
- Buyer contact details: `buyerName`, `buyerDesignation`, `buyerEmail`, `buyerMobile`
- Green Field delivery locations: array of `{ name, state, subLocationCount? }`
- Auction rules: `bidValidityDays` (default 180), `maxDecrements` (default 5), `extensionDurationMinutes` (default 15), `maxExtensionsPerBidder` (default 2), `currency` (default "INR")
- Optional fields: `supplyFrame`, `paymentTerms`, `signatoryName`, `signatoryDesignation`

**Vendor approval status (`AuctionApprovalStatus` in `types.ts`):**
- `not_sent` — document not yet sent to this vendor
- `pending` — awaiting vendor response
- `approved` — vendor confirmed participation, eligible to bid
- `rejected` — vendor declined participation
- `excluded` — manually excluded by sourcing team
- `overdue` — pending past deadline (computed from `vendorRevertDeadlineAt`)

Stored on `VendorInvite.auctionApprovalStatus` with timestamps:
- `approvalDocumentSentAt`, `approvalRespondedAt`, `approvalReminderSentAt`, `approvalExcludedAt`, `approvalExclusionReason`

**Key mutations in `capexContext.tsx`:**
- `saveAuctionApprovalDocument(requestId, document)` — stores the generated document
- `sendAuctionApprovalToVendors(requestId, vendorIds[])` — marks invites as `pending` and stamps `sentAt`
- `respondToAuctionApproval(inviteId, 'approved' | 'rejected')` — vendor-facing action via supplier portal
- `sendAuctionApprovalReminder(inviteId)` — stamps `reminderSentAt` and shows toast
- `excludeVendorFromAuction(inviteId, reason)` — marks as `excluded` with reason

**Eligibility helper:** `isVendorEligibleForAuction(invite, revertDeadline)` returns true only for approved vendors not past deadline. The `canStartAuction(invites, revertDeadline)` helper returns `{ canStart, approvedCount, pendingCount, rejectedCount, overdueCount }` — used to gate the Start Auction button (requires ≥1 approved).

**Document placeholder helpers in `auctionDocumentUtils.ts`:**
- `buildAuctionDocumentPlaceholders(request, document)` — generates all template placeholders including formatted dates (`DD/MM/YYYY`, `HH:MM Hrs`, `HH:MM AM/PM`)
- `AUCTION_APPROVAL_STATUS_LABELS` and `AUCTION_APPROVAL_STATUS_COLORS` — for UI badges

**Internal UI (`capex/[id]/page.tsx`):**
- Sourcing setup form with date/time pickers, auction rules with defaults
- Green Field delivery location entry (repeatable rows)
- Document preview with print support (browser print)
- Vendor approval tracker table: vendor name, sent at, response status, responded at, actions (reminder, exclude)

- If approved: shows waiting state until auction starts
- If rejected/excluded/overdue: shows non-participating state with contact info

**RFQ vs Reverse Auction (sourcing):** Brown Field is **RFQ-only by default** — there is no RFQ/Auction chooser; `capex/[id]` auto-sets `sourcingMode:'rfq'` when a Brown Field request enters `sourcing`, and a reverse auction can only be **escalated from RFQ** (and only with **≥2 vendor quotes**). RFQ uses `RfqPanel` (`src/components/RfqPanel.tsx`) and is a **vendor-quotes-first, per-line-item negotiation**. `RfqQuote` carries `linePrices` (unit price per `CapexLineItem.id`), `price` (base subtotal = Σ unit×qty), and footer charges (freight/packing/service/delivery/warranty/currency); grand total = `rfqTotal` = subtotal + freight + packing + service. The **vendor prices each line item** on the supplier portal (`proposeRfqQuote(...,'supplier')` → `pending_sourcing`); sourcing then **counters inline in the comparison grid** (per-line unit prices + footer, one vendor column at a time → `proposeRfqQuote(...,'sourcing')` → `pending_vendor`) or **accepts** the vendor's quote (`respondToRfqQuote(...,'approved','sourcing')`); the vendor accepts/counters/declines on the portal. Either side accepting → `approved`. `reopenRfqQuote(inviteId)` re-opens an approved quotation (`approved → pending_sourcing`, resets docs). `proposeRfqQuote` sanitizes input (price finite > 0; per-line + footer charges non-negative); `respondToRfqQuote` is turn-guarded. The panel uses the **reverse-auction comparison grid** (modeled on `VendorGrid`, shared field styles in `src/lib/auctionTheme.ts`): **line items as rows (Item / Description / Qty / HSN-GST), vendors as columns** with a **read-only HSN / GST** column per item row (vendor-entered, see GST section) and per-line unit price + line total and a green "↓ Lowest" highlight per line, footer attribute rows (freight/packing/service/delivery/warranty/currency), a Grand Total row with the L1 lowest highlight, and a per-line **Final Decision** column (a vendor dropdown defaulting to the lowest, recorded via `setRfqFinalVendor` → `CapexRequest.rfqFinalVendorPerItem`). Stacked per-vendor cards render below `lg`. The per-line **Final Decision** column is **identical to the reverse-auction grid** (`VendorGrid`): Price (₹) input + Disc (%) input + Vendor select + a computed `Price × Qty` net, persisted in `request.sourcingDecision` (`finalPrices` keyed `${itemId}-price`/`${itemId}-disc`, `finalVendorPerItem`). **Accept** still finalizes one vendor for the single-vendor PI/fulfillment. The sourcing **copy supplier link** is available on every vendor in every status (header + mobile card). A **"Start Reverse Auction"** CTA (enabled once **≥2** vendors have quoted) calls `seedAuctionFromRfq(requestId)` then `setSourcingMode('auction')`: `seedAuctionFromRfq` carries each vendor's RFQ quotation into the auction as an **opening `Quote`** (per-line `itemPrices`, grand total, footer charges, `seededByBuyer: true`) so the lowest is **L1** immediately and vendors can rebid lower via `submitQuote`. The auction setup also pre-fills its threshold with `lowestRfqTotal(reqInvites)` (editable). Sourcing requests a PI only once **both** the quotation and the documents are approved (`canRequestPi`). `VendorInvite` carries `rfqQuote`/`rfqStatus` (`not_sent`/`awaiting_quote`/`pending_sourcing`/`pending_vendor`/`approved`/`rejected`)/`rfqThread`; `effectiveRfqStatus` is tolerant of legacy data (an invited, un-quoted RFQ invite resolves to `awaiting_quote`). Legacy/simple requests with no `lineItems` render a single synthetic row (unit price = the whole quote).

**Unified Final-Decision award + per-vendor documents (2026-06):** the RFQ and reverse-auction comparison grids are **pure black-and-white** (no blue; the request number renders black) and behave identically. **Approval + Request-PI live only in the Final Decision area** via the shared **`FinalDecisionActions`** component (`src/components/FinalDecisionActions.tsx`), rendered below the grid in **both** modes — there are **no per-vendor "✓ OK / Select as Final / Request PI" buttons** anymore. - **The Final Decision persists as it is edited** — `VendorGrid.ItemRowGrid` writes `sourcingDecision` from an effect on every per-line vendor/price change, mirroring `RfqPanel.persistDecision`. It previously lived only in local component state, so `FinalDecisionActions` (which reads `request.sourcingDecision`) had nothing to group and showed its "pick a vendor and final price" placeholder **with no award button** until the separate **Save Final Decision** click. The effect is guarded by a JSON snapshot of the last write so persisting can't re-trigger it; Save still works as an explicit save.
- **`isAuctionMode` (`sourcingMode === 'auction' || ranAuction`) picks the grid footer**, not `ranAuction` alone. A request escalated to auction but never configured has no `auctionConfig`, so it fell through to the **legacy "Approve → buyer" footer** — clicking that is what pushed requests into `sourcing_approved` and stranded them. `auctionEnded` in the grid also now matches the page (`!ranAuction || isAuctionExpired(...)`), so an unconfigured auction counts as ended instead of showing "close the auction first".
- **`isLocked` no longer locks these flows**: it ignores the `approved` invite stamp when the request is award-based (a split award stamps each winning invite `approved` as it goes, which used to freeze the column while other lines were still unawarded), and applies the legacy `sourcing_approved`/`buyer_approved` lock only outside auction mode. A legacy single-vendor selection (`approveInvite`, not award-based) still locks.

The technical-spec gate is unchanged and still blocks the award per vendor — an unsent spec shows "Technical specification approval is pending …" with the buttons disabled, which is correct, not stuck.

**RFQ award unstick + fulfillment confidentiality (2026-08).** The same defect family, on the RFQ half and on the supplier portal. Six fixes:

- **RFQ split awards no longer dead-end.** Awarding one vendor bumps the request to `pi_requested`, which is in `RfqPanel`'s local `FULFILLMENT_STATUSES`, so `!inFulfillment` hid **both** `TechSpecPanel` and `FinalDecisionActions` and the remaining vendors could never be awarded — their line items were silently never ordered, and the request auto-completed once the first award's payments finished. `RfqPanel` now renders both while `!inFulfillment || splitAwardInProgress(...)`. The new **`splitAwardInProgress(lineItems, invites)`** / **`unawardedLineItemIds`** in `paymentUtils.ts` are deliberately narrower than the auction path's `|| awardBased`: "at least one vendor awarded AND at least one line still unawarded", so a **finished** award (single- or multi-vendor) correctly hides the surfaces again.
- **The status flow moved to `src/lib/statusFlow.ts`** (`ALLOWED_TRANSITIONS`, `PRE_PI_REQUEST_STATUSES`, **`canTransitionStatus(from, to)`**), imported into `capexContext` (which re-exports nothing — its only exports are `initialStatusForRequest`, `CapexProvider`, `useCapex`). UI call sites now **ask before acting** instead of firing a mutation `updateRequest` silently refuses. `sourcing → rejected` and `buyer_approved → rejected` were **missing edges** — the comparison grid's Reject button targeted exactly those and toasted "Request rejected" over a request that was still live. `payment_in_progress → rejected` is deliberately still absent (money has moved); the grid's Reject/Approve buttons check `canTransitionStatus` and say so rather than lying.
- **The legacy grid's "✓ Approve" no longer strands a request.** It writes `sourcing_approved`, which used to trip `isLocked` in `VendorGrid.ItemRowGrid` → read-only Final Decision column, both footers hidden, `FinalDecisionActions` showing only its "pick a vendor…" placeholder with no button, and no edge back to `sourcing`. The status half of `isLocked` is **gone for every mode** (not just auction) — `isLocked` is now `!!approvedInviteId && !isAwardBased(invites)`, preserving only the legacy single-vendor lock `approveInvite` relies on. Both statuses still reach `pi_requested`, so the award can finish.
- **A vendor who declines the contract documents is no longer locked out both ways.** The **Re-send documents** control lived only inside `VendorActions`' `rfqStatus === 'approved'` branch — unreachable, because declining the docs locks the quote form so a price can never be agreed. It now renders at **every** pre-approval status (`canManage && docStatus === 'rejected'`), and the decline is surfaced on the vendor's grid column header + mobile card. `resendDocApprovalPackage` resets the package to `pending`, which unlocks the supplier's quote form.
- **The INCO-terms award gate now actually binds** — `canRequestPi` was never called on any award path (only a hint string and a dashboard queue), so a foreign vendor with unsettled Incoterms could be awarded and PO'd. `awardAndRequestPi` / `finalizeSplitAward` / `requestProformaInvoice` now also reject **`incoTermsBlockedVendorIds`**, and `FinalDecisionActions` explains the block per vendor exactly like the tech-spec one. The enforced predicate is the new **`incoTermsNegotiationOpen`** (`pending_sourcing | pending_vendor | rejected`), **not** `incoTermsBlocksAward`, and it is scoped to **`sourcingMode === 'rfq'` only** — those are the only cases where both actors have a surface to settle on (sourcing's tracker is in `RfqPanel`, the vendor's card is in `RfqSupplierView`). `awaiting_vendor` is excluded because `inviteVendors` seeds it for every foreign vendor including auction ones, whose bid form never collects Incoterms. Enforcing the full `canRequestPi` would retro-block every auction award (no `rfqStatus`, no `docApprovalPackage`) and the normal RFQ split award (which awards straight from the Final Decision column without a formal Accept), so the doc-approval half is **not** enforced. A **rejected** agreement can now be re-opened by sourcing ("Edit & re-open with vendor" in the INCO tracker) so the gate can never dead-end.
- **Losing vendors no longer see the winner's fulfillment.** `RfqSupplierView` derived `fulfilled`/`piRequested` from `request.status` with no identity check, so every losing RFQ vendor was shown "Upload Proforma Invoice" and — on a single-vendor track — the **issued PO document**, the payment milestones and the trial-upload card (whose submission satisfied the QA gate on an order they never won). Both are now gated on **`ownsFulfillmentTrack(request, invite)`** (`paymentUtils.ts`), which covers **both** award shapes — `invite.awarded` for a split award, `request.finalVendorId` for the single-vendor RFQ/auction track — and fails closed. The `resolveFinalVendor` fallback for the displayed quote total is scoped the same way, so a non-winner can never be shown the winner's price. A losing vendor falls back to their own genuine RFQ state, so a split award still in progress keeps them negotiable.
- **"Start Reverse Auction" is pre-award only** — it kept its clickability into fulfillment and would re-seed opening bids, flip every vendor's supplier screen and switch the page to the auction view over an order already being paid. Hidden (and guarded in `startAuction`) once `inFulfillment || isAwardBased(invites)`.

**Per-vendor document selection at invite (`DocSelection`):** when sourcing invites vendors (RFQ picker in `RfqPanel`), each selected vendor gets a **checklist of documents to send for approval** — Commercial Terms, PBG, DLC, Payment Terms (`DOC_OPTIONS` in `docPackageUtils.ts`) **plus "Add custom document"** (free-form name + text → `DocApprovalPackage.extraDocs`). The choice is per-vendor (`DocSelection` in `types.ts`: `{ commercialTerms?, pbg?, dlc?, paymentTerms?, extraDocs? }`), threaded through `inviteVendors(requestId, vendorIds, docSelections?)` / `inviteNewVendor(..., selection?)` into `buildDocApprovalPackage(vendor, { selection })`, which now **omits** any unselected document. `defaultDocSelection(vendor)` preserves the legacy set (Commercial Terms + PBG + DLC, + Payment Terms for one-time vendors) when no selection is passed. `DocPackageReview` renders `extraDocs` and only shows the documents actually sent; `docPackageTitles(pkg)` drives the (now dynamic) supplier decline copy.

**GST via HSN — item-wise (`src/lib/hsnGst.ts`):** the HSN code is a property of **each line item** (`CapexLineItem.hsnCode`), **not** the vendor's quote — the same item carries one HSN across all vendors. **Only the vendor enters it** (required per line in their bid table — supplier `SupplierQuoteTable`/`SupplierQuoteCards` entry variant — atomically persisted on submit via `proposeRfqQuote(..., itemHsn?)`, which patches request line items in the same state pass). **Sourcing sees the HSN / GST column read-only** in the RFQ comparison grid (no dropdown); they cannot set or override it. GST is computed **per line** = `unit × qty × gstRateForHsn(item.hsnCode)` (see `rfqLineGstAmount`/`rfqLineGstRate`/`rfqLineBreakdown`); footer charges (freight/packing/service) are **not taxed**. `rfqGstAmount(quote, items?)` sums the per-line GST (legacy fallback to the deprecated quote-level `RfqQuote.hsnCode` when no items are passed); `rfqTotal(quote, items?)` = `rfqTaxableValue` (subtotal + freight + packing + service) + item-wise GST. `lowestRfqTotal(invites, items?)` likewise takes the line items. Per-line UI shows HSN, GST rate, pre-GST subtotal, GST amount, and GST-inclusive line total. The cross-tab `storage` listener re-syncs **both** `requests` and `invites` so HSN entered in the supplier tab is visible to sourcing for GST calculation. The grid's Grand Total row shows an `incl. ₹X GST` subtitle per vendor; the supplier Grand Total shows the item-wise GST line. (`RfqQuote.hsnCode` is retained only as a legacy fallback.)

**INCO Terms (Incoterms 2020) — answered WITH the quotation (`src/lib/incoTermsUtils.ts`):** sourcing can **quick-add a one-time vendor** by name/email/phone in the RFQ picker (`inviteNewVendor` → `Vendor.oneTime`, `contactPhone`), flagging **Foreign vendor** where applicable. Incoterms apply to **foreign vendors only** (`incoTermsRequired` keys on `Vendor.foreign`). **They no longer gate the quote form (2026-07).** The vendor prices their line items and clicks **Submit Quotation**; a **modal** (`IncoTermsModal` on the supplier portal) then presents the **Incoterms agreement — just two questions since 2026-09: Mode of Transport and Incoterms (the 11 Incoterms 2020 rules: EXW … FOB, CFR, CIF)** (`INCO_TERMS_QUESTIONS`; the other 10 legacy questions and their `IncoTermsDoc` keys were removed), and confirming it submits the **quote and the terms together in ONE atomic mutation** — `proposeRfqQuote(inviteId, quote, 'supplier', name, message?, itemHsn?, incoDoc?)` sets `rfqStatus: 'pending_sourcing'` **and** `incoTermsStatus: 'pending_sourcing'` in a single state pass. Closing the modal without answering leaves the quotation **unsent**. The invariant is enforced in the context, not just the UI: `proposeRfqQuote` **returns false** (persisting nothing) if a foreign vendor with an unanswered questionnaire submits without `incoDoc`, or if `incoDoc` is incomplete (`isIncoDocComplete`) / supplied for a non-foreign vendor. `needsIncoTermsWithQuote(invite, vendor)` decides when to ask (statuses `not_sent`/`awaiting_vendor` only) — re-quoting never re-asks. The counter-quotation path carries the same modal for legacy invites.

After submission the agreement **negotiates on its own track**, mirroring the RFQ price thread and looping until agreed: sourcing sees the answers in the **INCO Terms tracker** in `RfqPanel` (viewable at every stage, editable on their turn) and **approves** (`respondToIncoTerms`), **edits any field + writes a note to the vendor** (`IncoTermsDoc.revisionNote`) and sends it back (`proposeIncoTerms(...,'sourcing')` → `pending_vendor`), or **rejects**; the vendor sees the revision inline on the portal (`IncoTermsNegotiationCard`) and **accepts**, **sends back their own corrections** (`proposeIncoTerms(...,'vendor')` → `pending_sourcing`), or **declines**. Statuses `not_sent`/`awaiting_vendor`/`pending_sourcing`/`pending_vendor`/`approved`/`rejected` on `VendorInvite.incoTermsStatus` (+ `incoTermsDoc`/`incoTermsThread`). An unsettled agreement blocks the **award**, not the quoting — and since 2026-08 that gate is **enforced in the context**, not merely advertised: `awardAndRequestPi` / `finalizeSplitAward` / `requestProformaInvoice` reject any vendor for whom **`incoTermsNegotiationOpen(invite)`** holds (`pending_sourcing | pending_vendor | rejected`), scoped to `sourcingMode === 'rfq'`. The looser `incoTermsBlocksAward` (which also covers `awaiting_vendor`) still feeds `canRequestPi` in `rfqUtils.ts` and the RFQ panel's hint copy, but `canRequestPi` itself is **not** an award gate — see *RFQ award unstick + fulfillment confidentiality (2026-08)* for why enforcing its doc-approval half would dead-end the auction and split-award paths. Domestic / onboarded vendors never see the questionnaire.

**Document-approval package (RFQ + auction):** Commercial Terms + Performance Bank Guarantee + Delay Liability Clause are sent for vendor agreement; for **one-time / not-onboarded vendors** (flagged on the `Vendor` via the onboard modal, with `paymentTermsText` + `paymentSplits`), payment terms are included too. In **RFQ the documents must be approved BEFORE the vendor can enter a price**: when sourcing invites an RFQ vendor (`inviteVendors`, and the `setSourcingMode('rfq')` backfill), the `DocApprovalPackage` is built and `docApprovalStatus: 'pending'` is set up front. On the supplier portal the **quotation form is gated** (`docsBlocked`, mirroring the INCO-terms gate): the vendor sees `DocPackageReview` first and must **Accept** (→ `respondToDocApproval`) before the quote entry unlocks; declining shows a "Terms Declined" lock. (Legacy invites with no package fall through unblocked.) PI is still gated on **both** `effectiveRfqStatus === 'approved'` **and** `effectiveDocApprovalStatus === 'approved'` (`canRequestPi` in `rfqUtils.ts`) — docs are simply approved earlier now. `respondToRfqQuote`'s old auto-send on price agreement remains as a harmless no-op (its `docsAlreadyApproved` guard). If the vendor declines the documents, the supplier shows a "Terms Declined" state and sourcing can re-send via `resendDocApprovalPackage`; re-opening an approved quote (`reopenRfqQuote`) or sourcing countering an approved quote resets the documents. (`sendDocApprovalPackage` remains in context for standalone use.) The **reverse auction** embeds Commercial Terms (default) + PBG/DLC text on `AuctionApprovalDocument` (defaults from `docPackageUtils`), rendered in the print view and the supplier auction-approval screen — all three are agreed by accepting participation. Helpers/defaults in `src/lib/docPackageUtils.ts`.

**Proforma Invoice + Accounts + payments (two emailed links):** the finalized vendor uploads a PI on the supplier portal (`submitProformaInvoice` → `pi_submitted`, stamps `piSubmittedAt`); it surfaces to the buyer and the **Accounts Queue** (`/accounts/queue`, read-only). Neither accounts team has a portal login. Sourcing/admin share the public `/po/[token]` link from `AccountsPanel` (copy link + `EmailPreviewModal` → `PLANT_ACCOUNTS_EMAIL`); **Plant Accounts** assign **FA codes** per line (`assignFaCode`) and **Submit FA codes** (`submitFaCodes` → `accounts_processing` / award status, minting `poIssueToken`), which **auto-opens the email to Satish** with his `/po-issue/[token]` link. **Global Accounts ("Satish")** assigns the **PO number**, **uploads the PO document(s)** and **Issues the PO** (`issuePurchaseOrder` → `payment_in_progress`, stamps `issuedAt`/`issuedBy`; PO-doc base64 offloaded to IndexedDB; the vendor is notified and downloads the PO from a **Purchase Order card** on the supplier portal). Plant Accounts then return to their own link to tick the **payment milestones** (`markPaymentMade`) built from the vendor's `paymentSplits` (`src/lib/paymentUtils.ts`). `AccountsPanel` mirrors all of it read-only internally. Ticking the final milestone sets `tatStoppedAt` and moves to `completed`; each tick "notifies" the vendor (toast + supplier Payments card). Both modes converge here identically. The **auction** is awarded via the per-line Final Decision split award (see **Split award** above): after the auction **ends** (`isAuctionExpired`, via the countdown or **Close Auction Now** `closeAuction`), `finalizeSplitAward` marks each winning invite `awarded` — there is **no post-award doc-package** (vendors approved the pre-bid Business Rules — Commercial Terms + PBG + DLC — to bid), so sourcing requests each award's PI directly (`requestProformaInvoice`, `canFinalize` = `sourcing_head`/`super_admin`). **Supplier routing:** the finalized vendor routes into the shared PI-upload/fulfillment view (`RfqSupplierView`) for `pi_requested` **as well as** the `FULFILLMENT_STATUSES` (`pi_requested` is **not** in that list, so it must be matched explicitly — otherwise an auction winner at `pi_requested` could never upload the PI). (`PurchaseOrder` gained `poDocumentBase64`/`poDocumentName`/`poDocumentMimeType`/`issuedAt`/`issuedBy`; the legacy `createPurchaseOrder`/`submitPurchaseOrder` remain in context but the split flow uses `submitFaCodes`/`issuePurchaseOrder`.)

**Split award (multi-vendor reverse auction):** a reverse auction can be **awarded across multiple vendors** — different line items to different winners. Sourcing fills the per-line **Final Decision** column in `VendorGrid` (vendor + final price, GST-inclusive via `hsnGst`) and clicks **Approve Final Decision & Award** (`sourcing_head`/`super_admin`, gated until the auction has ended and every line has a vendor + price). `finalizeSplitAward(requestId, decision)` groups the lines by vendor (`buildAwardGroups` in `paymentUtils.ts`) and turns **each winning vendor's `VendorInvite` into a self-contained fulfillment track** via new invite fields: `awarded`, `awardedItemIds`, `awardAmount` (Σ net + item-wise GST), `awardStatus` (`awarded → pi_requested → pi_submitted → accounts_processing → payment_in_progress → completed`), plus per-award `faCodes`, `purchaseOrder`, `paymentMilestones`, `piSubmittedAt`, `tatStoppedAt`. A request is **award-based** when `isAwardBased(invites)` (any invite `awarded`). Helpers in `paymentUtils.ts`: `awardedInvites`, `isAwardInAccounts`, `awardSummary`, `deriveRequestStatus`. **Each award runs the full chain independently:** there is **no post-award terms step** (vendors approved the pre-bid Business Rules — Commercial Terms / PBG / DLC — to bid), so an awarded vendor sees a "You won — awaiting PI request" screen (`AuctionWinnerTerms`) and sourcing clicks **Request PI** per award directly (`requestProformaInvoice` sets the invite's `awardStatus`, not `finalVendorId`) → that vendor uploads its own PI (`submitProformaInvoice` → award `pi_submitted`) → **Plant Accounts** run that award's FA codes and payments on its own `/po/[token]` link and email **Satish** its `/po-issue/[token]` link for the PO (`assignFaCode`/`submitFaCodes`/`issuePurchaseOrder`/`markPaymentMade`, each with the `inviteId` arg — tokens are per award). The **request status stays coarse** for award-based requests (`pi_requested` while awards are in flight, `completed` once **all** awards complete — `ALLOWED_TRANSITIONS` allows `pi_requested → completed`); granular progress lives per-award. The fulfillment mutations take an **optional `inviteId`** that targets one award; omitting it keeps the legacy request-level behavior for RFQ / single-vendor. Surfaces that fan out per award: the per-award tracker on `capex/[id]` (Request PI / terms / live status per vendor), the **supplier portal** (each vendor sees only its `awardedItemIds` + its own PI/PO/payments, routed by `invite.awarded` + `awardStatus`), `AccountsPanel` (one read-only `AccountsTrack` + handoff link per award), and `/accounts/queue` (one row per award). TAT is per award.

**TAT + delay liability:** `src/lib/tatUtils.ts` `computeTat` — the clock starts at PI + 1 week; deduct **0.5%/week up to a cumulative 5%** (weeks 1–10), then escalate to **5%/week**; stops at `tatStoppedAt`. `TatBanner` (`src/components/TatBanner.tsx`) shows the live status on the request detail and supplier portal (recomputes every 60s); for split awards one banner renders per award (per-invite `piSubmittedAt`/`tatStoppedAt`/`awardAmount`).

**Adhoc head→head budget (`/capex/adhoc-budget`):** when a head exceeds its allocation, sourcing or plant_head raise an `AdhocBudgetRequest` to move budget from a head with spare to the over-budget head (same plant + FY, Brown Field). **Admin is the sole approver** (on `/capex/budget-approvals`). Approval writes per-head allocation overrides (`brownFieldHeadAllocations`, a `BrownFieldHeadBudget[]` alias of `GreenFieldHeadBudget` with `division = FLAT_MASTER_DIVISION`); master Brown Field head allocations prefer the override over the summed line-item budgets. Helpers in `src/lib/adhocBudgetUtils.ts`; mutations `createAdhocBudgetRequest`/`decideAdhocBudgetRequest`.

**Persistence:** `budgetProposals`, `adhocBudgetRequests`, `brownFieldHeadAllocations`, `kpiSnapshots` are persisted in `capex_data_v2` (read with `?? []`), alongside `cleanSlatePurgeVersion` (the one-time clean-slate purge stamp).

### Clean-slate purge (2026-07)

`applyCleanSlatePurge` in `capexContext.tsx` runs **once per browser** on load, guarded by comparing the stored `cleanSlatePurgeVersion` against `CLEAN_SLATE_PURGE_V1` (`mockData.ts`). It drops **workflow + Brown Field planning data**: `requests`, `invites`, `chatMessages`, `adhocBudgetRequests`, `budgetProposals`, `brownFieldHeadAllocations`, **`kpiSnapshots`**, and the **entire IndexedDB blob store** (`putAllFiles({})` — PIs, PO documents, trial uploads, tech-spec sheets, quote/line-item attachments all hang off those records, so nothing is orphaned).

**`kpiSnapshots` IS purged, even though it is a measurement rather than workflow data.** Every stock metric it records — allocation, commitment, utilisation, over-exposure, open sourcing load — is measured over *the requests and budget rows the purge deletes*. Keeping the history would leave a series describing records that no longer exist, and the wipe would render as a **cliff** in every chart: a dramatic drop that never happened, which is exactly the confident-but-wrong figure `kpiSnapshots.ts` exists to refuse. Measurement history is only meaningful against the data it measured.

**The corrupt-payload salvage is PURGE-AWARE — this is the gate with no unit coverage.** If `JSON.parse` of `capex_data_v2` throws, the load `catch` makes a second, isolated attempt to recover **only** `kpiSnapshots` (so one malformed workflow record does not cost the whole measured history), and it salvages **only when `salvaged.cleanSlatePurgeVersion === CLEAN_SLATE_PURGE_V1`**. The purge decision is made early in the `try`, but `kpiSnapshots` is restored late — so on a payload that is corrupt *and* purge-pending, salvaging blind would resurrect pre-purge points onto requests/invites that the purge is about to wipe, manufacturing that same fake cliff. A purge-pending payload therefore yields an empty history, and the app still loads. This gate lives inside `CapexProvider`'s load effect and is **not reachable from the pure layer, so it has no unit test** — it is verified by a live corrupt-payload load.

**Brown Field live FY is cleared separately** — `BROWNFIELD_SEED_VERSION` is `fy2026_27_cleared` with an **empty** `brownFieldSeedData`, so on load every stored Brown Field master row is replaced with nothing. Authors rebuild FY 2026-27 from Budget Planning (`/capex/budget-proposals`). The Excel import **Template** still ships Jhajjar Plant 1 worked examples via `FALLBACK_SAMPLES` in `bulkMasterImport.ts` when the plant has no live rows yet.

**Green Field data is deliberately NOT purged** — Green Field master rows and `greenFieldBudgetAllocations` (plant/section/head envelopes), plus `vendors`, `customPlants`, `masterHeads`, `plants` and `categories` all load normally.

**Bump `CLEAN_SLATE_PURGE_V1` to re-run the wipe** on every browser. The constant is at **`'clean_slate_v3_budget'`** (bumped 2026-07-29 to clear workflow + budget proposals / head overrides alongside the empty Brown Field seed). `resetData()` remains the nuclear option — it clears localStorage entirely, Green Field included.
